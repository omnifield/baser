# baser

**Фундамент-фреймворк Omnifield** — переиспользуемые капабилити (`@omnifield/baser-*`), построенные на рыночном каноне (rebuild-on-canon), а не на самопале.

- **Канон продукта — раздел `BASER2` в knowledger**, и только он: `kb:BASER2-2` (что такое станок), `kb:BASER2-4` (рабочая аналогия), `kb:BASER2-5` (где живут настройки), `kb:BASER2-12` (форма ответа). Старый раздел `BASER` — **legacy**: там описана механика владения, которой больше нет, и читать его как руководство нельзя.
- Решения: `ADR-15` (split), `ADR-19` (релизный реестр = публичный npm), `ADR-20` (гринфилд на Nx).
- Именование пакетов: `@omnifield/<product>-<package>` (MECH-15).

## Где брать пакеты

**Сегодня они живут в GitHub Packages, а не в публичном npm.** Публичный npm — это релизный поток, и он ещё ни разу не выполнялся: `nx release` описан ниже, но выпуска не было. Пока идёт дев-поток.

Потребителю нужны две строки в пользовательском `~/.npmrc` — токен с правом `read:packages`:

```
@omnifield:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=<токен>
```

В omnifield-девбоксах это уже настроено: `NPM_CONFIG_USERCONFIG` указывает на общий том `omnifield-secrets`, и токен там лежит. Ставить руками ничего не нужно.

**Даже публичные пакеты GitHub Packages требуют токен на чтение** — это свойство сервиса, а не наша настройка. Без него `npm i @omnifield/baser-devbox` ответит «404, пакета нет», и человек пойдёт искать несуществующий пакет вместо своих кредов.

### `403` в CI потребителя — это наш недоданный grant, а не твой кривой токен

`GITHUB_TOKEN` чужого workflow имеет `packages: read`, но **пакета для него не существует**, пока в настройках пакета не добавлен репозиторий-потребитель (Package settings → Manage Actions access). Пока grant не выдан, конвейер потребителя ловит `403` на установке — и чинит, естественно, свой токен, потому что искать причину у нас ему неоткуда.

Grant нужен на **всю цепочку**, а не на верхний пакет: `baser-cli` тянет `check`, `contracts`, `materialize`, `pack`. Первым `403` ловится тот, что резолвится раньше.

**Это шаг ВЫПУСКА, а не разовая галочка:** обвес по определению ставится в чужой репозиторий, значит каждый новый потребитель требует grant поимённо (`tasker:BASER2-126`). В чек-листе выпуска он стоит последним пунктом.

Снимется это по построению, когда дверь начнёт доставать обвес сама (`tasker:BASER2-113`) — CI потребителя перестанет ходить в наш реестр вовсе. Grant — мост до тех пор.

## Стек
- **Монорепо-движок:** [Nx](https://nx.dev) (package-based, pnpm) — генераторы, project-graph, `nx release`.
- **Релизный поток:** `nx release` (independent, Conventional Commits) → публичный npm, OIDC trusted publishing + provenance. Ещё не запускался.
- **Без Nx Cloud** — локального кэша достаточно для фундамент-монорепо.

## Разработка
```sh
pnpm install
pnpm verify                                # готовность: тесты + типы + сборка
pnpm exec nx release --dry-run             # предпросмотр релиза
```

**`pnpm verify` — единственная команда, которая значит «готово».** Готовность выражалась тремя целями, и за один день дважды случилось одно и то же: прогнали `test`, сказали «зелено», а `typecheck` был красный. Инструменты отработали честно — `vitest` типы не смотрит по построению. Дыра была в том, что готовность приходилось помнить, а не вызывать.

Команда гоняет **всю монорепу, а не одну зону**: при изменении общей формы зоны зелёными порознь быть не могут — приёмки берут предметом живой пакет соседа. И гоняет **без кэша**: у части зон эталон приёмки лежит вне их проекта, и кэш уже отдавал зелёное по устаревшему состоянию файла (`tasker:BASER2-78`).

## Вклад

**Заголовок PR обязан быть по Conventional Commits: `<тип>(<зона>): <что сделано>`.** Мы мержим сквошем, поэтому заголовок PR — это и есть коммит в `main`, а `nx release` выводит по нему версию и changelog. Заголовок без типа оставит изменение невидимым для выпуска, а ломающее (`!`) не поднимет мажор. Проверяется в CI.

```
feat(materialize): класс артефакта в паспорте укладки (BASER2-51)
fix(cli): дверь не сочиняет версию, которой обвес не назвал
feat(devbox)!: объявление на форму 2
```

## Релиз

`nx release` управляет версиями и changelog, база сравнения — теги `<имя пакета>@<версия>`. Публикация релизного потока — воркфлоу `release.yml` (`workflow_dispatch`, ручной), OIDC + provenance на публичный npm. Идемпотентно: уже изданная версия — skip, не fail.

**Номер на нулевых мажорах назначает человек, а не считалка.** Пока пакет младше `1.0.0`, `nx` поднимает патч и фиче, и ломающему — проверено прогоном 2026-08-01, явное соответствие типов в `nx.json` этого не меняет (`tasker:BASER2-95`). Поэтому бамп указывается явно (`nx release version minor --projects=…`), а причина называется в PR выпуска.

**Невранье держит гейт, а не дисциплина:** `tools/release-guard.mjs` (job `release-guard` в CI) краснеет, если пакет получил с прошлого тега ломающий коммит — `!` в заголовке или `BREAKING CHANGE` в теле, — а номер поднят слабее, чем требует конвенция: минор при `0.x`, мажор при `1.0.0` и старше. Версия не двинулась — гейт молчит: на обычном PR выпуска нет.

Уйдём с нулевых мажоров — считалка станет честной сама, и гейт останется страховкой.

### Чек-лист дев-выпуска

1. `pnpm verify` зелёный целиком — вся монорепа, без кэша;
2. номера проставлены руками в `package.json`, причина каждого названа в PR выпуска;
3. **вся цепочка**, а не только изменившийся пакет: внутренние зависимости объявлены как `workspace:*` и превращаются в точные номера при публикации. Выпустишь одну дверь — у потребителя окажутся две версии контрактов в одном дереве;
4. `node tools/release-guard.mjs` зелёный (он же стоит в CI);
5. PR выпуска влит, `main` чистый;
6. `pnpm publish --no-git-checks` из каталога каждого выпускаемого пакета — **не `npm publish`**: он оставляет `workspace:*` в манифесте, и пакет не устанавливается вовсе;
7. проверить факт **в реестре** (`npm view <пакет> version`), а не по выводу публикации;
8. теги `<имя пакета>@<версия>` на коммит выпуска, `git push origin --tags` — это база сравнения для следующего раза и для гейта;
9. **grant новым потребителям** — поимённо по цепочке (см. «`403` в CI потребителя» выше). Пропустишь — конвейер потребителя встретит нас `403`, и чинить он будет свой токен.
