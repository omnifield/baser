# `@omnifield/baser-cli` — дверь

**Раннер, который зовёт станок и кладёт файлы на диск, — и входная точка к
подготовке обвеса.** Движок работает только
с виртуальным деревом и файловой системы не касается вовсе
(`packages/baser-materialize`), форма ничего не читает и ничего не исполняет
(`packages/baser-contracts`) — до этого пакета станок физически невозможно было
позвать (`tasker:BASER2-18`, `tasker:BASER2-20`).

```
baser.json + package.json обвеса        ← дверь читает
         ↓ resolveSettings                (контракты)
  значения + движение дефолта           ← дверь НАЗЫВАЕТ до применения
         ↓ checkTemplate → EJS            (форма решает, дверь рендерит)
  готовое содержимое → CanonSource      ← движок значений не видит
         ↓ computePlan / applyPlan        (движок)
  виртуальное дерево → flushChanges     ← дверь кладёт на реальную ФС
```

## Команды

```
baser plan   показать план, ничего не применяя
baser apply  применить план и записать на диск

baser check  <каталог обвеса>                 деталь подходит патрону?
baser pack   <каталог обвеса> --into <куда>   собрать нагрузку к выдаче
baser bundle <каталог обвеса> --into <куда>   собрать запускаемый бандл

--json            отдать ответ данными (то же, поверх чего рендерится текст)
--cwd <path>      корень репозитория потребителя (по умолчанию — текущий каталог)
--confirm <dest>  подтвердить перезапись ЭТОГО чужого артефакта, поимённо
--into <path>     каталог выдачи для pack и bundle
--version         версии схем: двери, формы, вывода движка, бандла
```

Две семьи команд. **Материализация** (`plan`/`apply`) кладёт файлы в репозиторий
потребителя. **Подготовка детали** (`check`/`pack`/`bundle`) готовит обвес к
выдаче: раз патрон наш, то и «проверь, что деталь встаёт» — наш инструмент
(`kb:BASER2-9`).

Механики подготовки живут в соседних зонах (`baser-check`, `baser-pack`); дверь
их зовёт и отдаёт ответ данными плюс текст поверх. **Своей семантики поверх
чужой она не изобретает**: коды приходят снизу, `describeProblems` контрактов
печатает и свои отказы, и чужие. Вторая правда о чужом событии нам уже дважды
выходила боком.

Две фазы разнесены двумя КОМАНДАМИ, а не флагом одной: читаемость плана до
применения — инвариант, а не удобство (рынок подтвердил дважды независимо —
`nx migrate` и схематики).

| код возврата | что                                                   |
| ------------ | ----------------------------------------------------- |
| `0`          | сделано либо делать нечего                            |
| `1`          | движок отказал: конфликт владения, решать потребителю |
| `2`          | дверь отказала: вход непригоден, чинить конфиг/обвес  |

## Обязательства двери

### Ноль вопросов пользователю

Ни одного промпта, ни одного обращения к `stdin`, ни флага «неинтерактивный
режим»: режима, который надо выключать, не существует. Не заполнено — работает
дефолт обвеса. **В CI команда ведёт себя ровно как у человека** — не потому что
так задумано, а потому что другого поведения у неё нет.

### Движение дефолта названо ДО применения

Движок этого сказать не может — он значений не видит вовсе
(`tasker:BASER2-23`). `resolveSettings` контрактов отдаёт только КОНЕЧНОЕ
происхождение значения, а «подниму версию с 22 на 24» — утверждение про два
конца. Поэтому дверь восстанавливает цепочку разрешения целиком:

```
network  null → "omnifield-gateway"  дефолт обвеса, затем пресет omnifield — поедет за выпуском обвеса
runtimeVersion  "24" → "20"          дефолт обвеса, затем заполнено тобой — не поднимется никогда
```

Цепочка строится из тех же данных, что и разрешение, и **сверяется с его
результатом**: рассказ о значении, разошедшийся с самим значением, хуже
отсутствия рассказа, поэтому расхождение бросает, а не копится отказом.

В тексте этот блок печатается ВЫШЕ плана. Порядок не косметика: человек читает
сверху вниз, и движение, названное ниже списка шагов, прочиталось бы уже после
решения.

> **Чего дверь назвать НЕ может, и почему.** Движение дефолта МЕЖДУ ВЫПУСКАМИ
> обвеса («вчера резолвер отдавал 22, сегодня 24») недоступно: прежнее значение
> нигде не хранится. Служебная запись (`tasker:BASER2-4`) появилась, но помнит
> она ЧТО положено — `dest`, `src`, обвес, хеш, — а не С КАКИМИ ЗНАЧЕНИЯМИ.
> Место для них теперь есть, самой дельты пока нет: это названная граница, а не
> забытый угол. Дверь называет то, что знает достоверно, и не выдумывает второй
> конец. Расхождение самого артефакта при этом видно всегда: его несёт
> `step.previous` движка.

### Вывод машинночитаем в первую очередь

Команда сначала СОБИРАЕТ `DoorResult` и только потом что-то печатает.
`renderText` принимает эту структуру целиком и больше ничего — ни репозитория,
ни декларации, ни движка. Так «текст — рендер поверх тех же данных» держится
формой функции, а не обещанием: чего нет в ответе, то человеку показать нечем.

Своей семантики поверх соседей дверь не изобретает: план, отчёт применения и их
коды приезжают от движка как есть, отказы формы — с кодами контрактов. Свои коды
только там, где сказать больше некому (`DoorProblemCode`).

Три версии схем едут в ответе вместе, потому что зоны выпускаются порознь:
`doorSchemaVersion` (форма ответа двери) · `formVersion` (объявление и конфиг) ·
`outputSchemaVersion` (вывод движка).

### `plan` не пишет ничего

Обе команды идут по одному пути и строят одно и то же дерево; расходятся они
ровно на последнем шаге — сбросе. План, посчитанный по другому состоянию, чем
применение, не был бы планом. Список `writes` у `plan` пуст ПО ПОСТРОЕНИЮ; что
ляжет, читается из `plan.steps` и `config.creates`.

### Сходимость мерится прогоном целиком

`status: 'converged'` означает «делать нечего», а не «у движка нет шагов».
Конфиг, который дверь родит этим прогоном, движок своим шагом не считает и
считать не может — он о нём не знает. Гейт, спросивший «сошлось?» и получивший
«да» там, где `apply` ещё поменяет репозиторий, зеленел бы вхолостую.

## Трейсы

`result.trace` несёт спаны фаз ДВЕРИ: `door.config` · `door.declaration` ·
`door.resolvers` · `door.values` · `door.render` · `door.flush`. Спаны движка
живут отдельно, в `plan.trace` и `applied.trace`.

Списки не сведены намеренно: потребитель, увидевший медленный прогон, обязан
отличить разбор служебной записи (зона движка) от чтения десятка
шаблонов с диска (зона двери) — это разные починки в разных пакетах.

`door.resolvers` — событие со счётчиком, а не спан с длительностью: загрузка
модулей резолверов асинхронна, а спаны синхронны. Это не недосмотр — резолвер
обязан быть синхронной чистой функцией, асинхронна только доставка модуля;
врать нулевой длительностью хуже, чем не мерить.

Трейсы — телеметрия, а не печать в поток: в текстовый рендер они не идут.

## Конфиг потребителя

Дверь его **читает**, а создаёт ровно один раз — когда файла нет вовсе. Засев
идёт по объявленным зависимостям потребителя: обвес это пакет, объявивший блок
`baser`, и другого признака у него нет. Версию формы проставляет дверь,
пользователь не вводит ничего (`kb:BASER2-5`).

**Существующий конфиг авторитетен целиком.** Засев работает только на пустом
месте: иначе снятый пользователем обвес возвращался бы в конфиг сам, и
отказаться от поставленного пакета стало бы нечем.

Пустой конфиг не кладётся: файл, объявляющий ноль обвесов, — мусор в чужом
репозитории, а не миграционный крючок.

`config.creates` — настоящее время: у `plan` это намерение (он не пишет), у
`apply` — факт. Что действительно легло на диск, говорит `writes`, и только он.

## Шов `contentRoot`

Обвес объявляет корень содержимого ОТНОСИТЕЛЬНО СВОЕГО ПАКЕТА, а движок адресует
источник путём ОТНОСИТЕЛЬНО ДЕРЕВА ПОТРЕБИТЕЛЯ и этим же путём защищается от
записи в собственный источник (`dest-in-content-root`). Перевод одного в другое
возможен только в двери — и не всегда возможен вовсе.

| раскладка                                     | что подаёт дверь                    | защита движка           |
| --------------------------------------------- | ----------------------------------- | ----------------------- |
| штатная (`node_modules/…` внутри репозитория) | настоящий репо-относительный путь   | работает в полную силу  |
| hoisted-workspace · `npm link` · глобальная   | форма «источника в этом дереве нет» | вырождена ПО ПОСТРОЕНИЮ |

Во втором случае репо-относительного пути не существует: `toRepoPath` режет и
абсолютный, и `..`. Подделать его нельзя — подделка выглядела бы как защита, а
защищала бы пустоту, и настоящий источник, окажись он потом внутри дерева по
другому пути, остался бы незакрытым. Поэтому факт называется формой.

Форма `contentRoot: null` принята типом движка, и случай он называет сам —
`SourceOutsideTreeError`. Дверь пробрасывает его код и дописывает единственное,
чего движок не знает: путь, по которому обвес физически установлен.

## Служебная запись: `baser.lock.json`

Владение больше не доказывается наклейкой внутри артефакта — оно выводится из
записи сбоку, которую пишет движок (`tasker:BASER2-4`). Дверь эту запись не
трогает: она уезжает на диск тем же сбросом, что и артефакты, и попадает в
`writes` наравне с ними.

> **Файл обязан коммититься.** Без него следующий прогон не может доказать
> владение НИ ОДНИМ артефактом и берёт их как чужие: план упирается в отказы
> `foreign-dest` по всему дереву. Это правильное поведение — без записи владение
> недоказуемо, — но потерять её значит потерять владение.

### Почему файлы оказались чужими — два состояния, два сообщения

Для движка «записи нет» — ОДНО состояние, и он честно объявляет артефакты
чужими. На деле состояний два, и чинятся они по-разному. Различает их **конфиг
потребителя** — сигнал, которого у движка нет и быть не должно:

| что видно                 | код                | что человеку делать            |
| ------------------------- | ------------------ | ------------------------------ |
| конфиг есть, записи нет   | `manifest-missing` | восстановить запись из истории |
| нет ни конфига, ни записи | `first-install`    | ничего не сломано — выбрать    |

**Первая установка в непустой репозиторий — самый обычный случай**: у живого
репозитория уже что-то лежит на этих местах. Человек не потерял ничего, поэтому
и сообщение не про потерю: его файл НЕ ТРОНУТ, отказ движка — это отказ заменить
чужое. Дальше он выбирает, и оба выхода стоят рядом с ценой каждого: пусть файл
ведёт обвес (`--confirm <путь>` — замена целиком, правки руками дальше не
переживают) либо снять обвес и оставить своё. Подсказка про `--confirm` не должна
читаться как «жми сюда, чтобы затереть своё», поэтому цена согласия названа в том
же предложении, что и само согласие.

Одно сообщение на оба состояния уже соврало на живом репозитории
(`tasker:BASER2-28`): человека с его собственным `.devcontainer` уверенно послали
восстанавливать из истории запись, которой там никогда не было. Уверенный
указатель не туда хуже отсутствующего — он тратит чужое время.

Признак не абсолютен: конфиг можно написать и руками, не запуская дверь.
Различить это дверь нечем — прежнего состояния она не хранит, — и **вместо второй
догадки сообщение отдаёт человеку дешёвую проверку** («посмотри в историю») и
верное действие на каждый из двух исходов. Когда различить нельзя, честнее отдать
критерий, чем угадать за человека.

Молчание здесь было бы дефектом, но и крик — тоже: условие узкое (записи нет И
есть отказы `foreign-dest`), поэтому в пустом репозитории дверь молчит.
Предупреждение, которое видит каждый новый потребитель, за неделю перестаёт
читаться.

**Оба обещанных пути прогоняются тестом, а не только написаны.** Это у нас уже
дважды сработало.

Битая запись — отказ движка со своим кодом `manifest-unreadable`; дверь его
пробрасывает как есть.

## Ручная выдача: запускаемый бандл

`pack` собирает нагрузку и про способ доставки не знает — собрать всегда одно и
то же, вынести можно папкой в руках, в реестр, в локальный том
(`tasker:BASER2-31`). `bundle` берёт ровно один способ — папку в руках — и
добавляет к нагрузке то, без чего она не запускается: саму дверь.

**Дверь вкладывает себя, и только она.** Не из вежливости к слоям: вложить себя
может лишь тот, кто знает, из чего состоит. Сделай это `pack` — он зависел бы от
двери, а дверь зависит от него, и круг замкнулся бы. Направление
`contracts ← check ← pack ← дверь` держится именно этим.

`bundle` — отдельная команда, а не флаг у `pack`: флагом это выглядело бы как
настройка упаковки и стёрло бы различение «подготовка ≠ доставка», на котором
построена вся цепь.

```
выдача/
  INSTALL.md      инструкция под КОНКРЕТНЫЙ обвес, а не шаблон
  install.mjs*    установка в чужой репозиторий (шебанг И бит — запуск напрямую)
  baser.mjs*      дверь после установки
  payload/        нагрузка от pack — сам обвес
  payload.json    опись
  node_modules/   дверь и её зависимости
```

Ни тарбола, ни бандлера: Node резолвит от места файла вверх, поэтому
`node_modules` внутри папки — уже рабочий механизм. Бандл ~1 МБ.

### Почему дверь держит виртуальное дерево сама

Движок работает только с `Tree`, и раньше дверь брала для этого `FsTree` из
`nx`. В монорепе это работало; в унесённой папке — нет: `nx` это 21 МБ и
платформенные нативные модули, то есть бандл переставал работать ровно там, где
обещано «унесли и заработало».

Цена вопроса оказалась **шесть методов** — `read` · `write` · `exists` ·
`isFile` · `children` · `delete`. Дверь держит их сама (`tree.ts`), `@nx/devkit`
остался зависимостью ТИПА, а в рантайме двери его нет вовсе. Настоящих
зависимостей две: `ejs` (252 КБ, без своих зависимостей) и `tslib`.

### Развилка: как дверь находит обвес в ручном флоу

Дверь ищет обвес резолвом от корня репозитория потребителя — в его
`node_modules`. В ручной выдаче обвес лежит в бандле, и вариантов было два:

|                                                       |                                 |
| ----------------------------------------------------- | ------------------------------- |
| **(а)** установщик кладёт обвес в `node_modules` цели | грубо, зато не трогает контракт |
| **(б)** форма учится указывать локальный источник     | чище на вид                     |

**Выбрано (а).** Второе — изменение контракта ради ВРЕМЕННОГО способа доставки,
а такие изменения остаются навсегда: «локальный источник» пришлось бы держать и
после того, как появится публикация. Первое честно повторяет пакетный менеджер и
ничего не обещает сверх этого — `npm i` поверх заменит поставку на месте, и
дверь разницы не заметит, потому что её нет.

Прогон показал, что «повторяет пакетный менеджер» надо понимать буквально:
менеджер кладёт не только файлы, но и запись в `dependencies`, а дверь ищет
обвесы именно по объявленным зависимостям. Установщик, копировавший только
каталог, получал «обвесов не поставлено» — половина имитации оказалась хуже её
отсутствия.

Второй прогон, уже на живом чужом репозитории, показал границу этой имитации —
см. ниже: полной она быть не может в принципе.

## Первые пять минут человека с бандлом

Три дефекта (`BASER2-33`, `BASER2-34`, `BASER2-35`) нашлись за две минуты живого
переезда на weber и **ни один — за 410 зелёных тестов**. Общее у них не участок
кода, а место жизни: среда и переходы между «собралось» и «человек запустил».
Поэтому и пробы на них спрашивают то, чего не спрашивает сборка
(`first-five-minutes.spec.ts`).

### Шебанг есть — бит исполнения обязан быть тоже

`install.mjs` и `baser.mjs` кладутся в бандл с битом (`0o755`). Шебанг в них был
с самого начала, то есть прямой запуск был ОБЕЩАН, а держался этот обещание
намерением: человек набирал `./install.mjs` и получал `Permission denied` —
сообщение операционной системы про права, хотя дело не в правах. Тот же класс,
что копирование обвеса без записи в `dependencies`.

Обещание симметрично и проверяется в обе стороны: шебанг без бита — ложное
обещание, бит без шебанга — сломанный запуск.

**Что мы обещаем про дорогу.** Права переживают `tar` и обычное копирование —
именно этим бандл и уносят, и именно на распакованном из архива проба и гоняется
(на свежесобранном бит стоял бы и без нас). Дорог, которые прав не несут
(архиваторы Windows, выгрузка через браузер), мы не обещаем — и `INSTALL.md`
говорит это прямо, отправляя на `node install.mjs`, которому права не нужны
вовсе.

### На хосте Node нет — и по канону быть не должно

Инструмент, который затаскивает проект в контейнер, требовал Node НА ХОСТЕ
(`kb:FUND-4`: на хосте только докер и файлы). Курица и яйцо: чтобы попасть в
контейнер, нужен `.devcontainer`; чтобы его получить — запустить установщик;
чтобы запустить установщик — нужен Node, которого на хосте нет.

Не увидели мы это потому, что **все прогоны шли внутри девбоксов, где Node есть
по умолчанию**: предусловие выполнялось само собой и оттого не было названо
нигде.

Лечится ДОКОЙ: в `INSTALL.md` первой командой идёт запуск через одноразовый
контейнер, `node install.mjs` — вторым, с явной пометкой «если Node уже есть».
Шелл-запускалки в бандле нет и не будет: она добавила бы в поставку скрипт и
предположение про докер ради экономии одной команды.

### Ручная доставка не оставляет того, что нельзя закоммитить

Запись в `dependencies` нужна двери, чтобы найти обвес, — и **не резолвится ни у
кого, кроме того, кто держит бандл в руках**: пакет нигде не опубликован.
Закоммитил `package.json` — у коллеги падает `pnpm install`, первым падает CI.

Это не дефект двери и не дефект контракта, а **цена временного способа
доставки**. Через реестр всё сходится само: менеджер и файлы положит, и строку
напишет, и лок обновит. Поэтому:

- запись живёт **ровно прогон** — снимок манифеста берётся до неё, уборка идёт в
  `finally`, отказ двери на неё не влияет (отказ — штатный исход, а не повод
  оставить мину);
- убирается **всегда** — и после `--plan`, и после установки. `--plan` мутировал
  чужой манифест ДО всякого плана, а человек набирает его со смыслом «просто
  посмотреть»;
- `package.json`, которого до нас не было, удаляется **целиком**: в Go- или
  Python-репозитории это чужеродный файл, а не лишняя строка;
- возврат **побайтовый**: чужой файл не должен даже переформатироваться —
  разошедшийся отступ это тоже строка в `git status`, которую не просили;
- установщик **говорит, что убрал**. Молчаливая уборка — тоже молчание.

**Контракт двери при этом не тронут.** Способ поиска обвесов по объявленным
зависимостям остался как был: уборка живёт в `install.mjs` — файле,
существующем ровно ради ручной доставки, — и умрёт вместе с ним, когда появится
публикация. Контракт, изменённый ради временного костыля, переживает костыль.

`pnpm-lock.yaml` не трогается: чужой лок-формат — чужие внутренности. Значит
имитация менеджера полной быть не может в принципе, и достраивать её незачем —
после публикации ручная запись всё равно расходилась бы с локом.

> **Уборка не отменяет установки.** Дверь после неё обвес по-прежнему видит:
> сразу после первого `apply` авторитетен `baser.json`, а он остаётся и
> коммитится. Вопрос очевидным не был и потому задан пробой, а не предположен.

### Самодостаточность проверяется, а не заявляется

Замыкание зависимостей считается по объявленным `dependencies` — но это
ОЖИДАНИЕ. Гарантию даёт последний шаг сборки, и он состоит из двух утверждений:

1. каждый импорт по имени **в нашем коде** резолвится внутри бандла;
2. у каждого вложенного пакета все его объявленные зависимости тоже внутри.

Внутренние файлы чужих пакетов при этом не судятся: `ejs` везёт браузерную
сборку, свой CLI и jakefile, которые никогда не грузятся, и объявлять бандл
сломанным из-за них — ложная тревога. Тот же принцип, по которому `check` не
переписывает семантику `files`, а `pack` не переписывает `.npmignore`.

Настоящее доказательство даёт не этот шаг, а приёмка: бандл уносится и
запускается.

## Чего здесь нет

`check-drift` и `fork` как команды (`BASER2-15`, A6) — они поверх форка, которого
ещё нет. Форма ручек в пульте — этап C.

**Много источников целиком (A5) тоже нет, и это отказ, а не пробел.** Форма
допускает несколько обвесов с первого дня, а движок сегодня — нет: план строится
по ОДНОЙ декларации, а сироты ищутся по всем записям манифеста, поэтому два
прогона подряд сняли бы артефакты друг друга как потерявшие объявление. Дверь
называет это `multiple-sources` с причиной, а не портит дерево молча.

## Приёмка

```
npx vitest run --config packages/baser-cli/vitest.config.mts
```

Приёмка не мок: обвес девбокса ставится в `node_modules` чистого временного
репозитория ровно так, как его положил бы npm, дверь зовётся своей публичной
поверхностью, файлы уезжают на настоящий диск, а эталон — **живой
`.devcontainer` этого репозитория**. Обвес берётся из принятого примера зоны
контрактов (`examples/devbox`), а не переписывается: две копии одного обвеса
разъехались бы, и приёмка начала бы зеленеть на обвесе, которого нет ни у кого.

**Приёмка идёт по НАСТОЯЩЕЙ раскладке обвеса, без обходов.** Прошлая версия
подменяла `dest` на `.jsonc`, потому что живой `devcontainer.json` движок пометить
не мог; с переездом записи сбоку (`tasker:BASER2-4`) обход снят, и `.ejs` ложится
прямо туда, куда его целит обвес. Цель итерации — «поставил пакет → позвал
команду → `.devcontainer` лёг» — впервые проверяется целиком.

Проверяются ПЕРЕХОДЫ, а не устойчивые состояния — в устойчивом состоянии всё
сходится с первого раза:

| переход                                 | что обязано произойти                                                  |
| --------------------------------------- | ---------------------------------------------------------------------- |
| чистое дерево → разложено               | живой JSONC на диске, запись в манифесте, сходится с эталоном          |
| `render: false`                         | ложится байт в байт: движок содержимого не трогает                     |
| тот же прогон второй раз                | `converged`, ни шага, диск не тронут                                   |
| обвес обновился, дефолт поднялся        | движение названо до применения; артефакт догоняет                      |
| то же, но значение заполнено            | не поднимается — подниматься неоткуда                                  |
| пресет убран из конфига                 | цепочка укоротилась, слой не развернулся вовсе                         |
| артефакт правили руками                 | перегенерация целиком; прежнее содержимое в `step.previous`            |
| запись ушла из раскладки                | артефакт снят с ДИСКА, а не только из виртуального дерева              |
| на месте артефакта чужой файл           | отказ; `--confirm` снимает поимённо и на соседний не масштабируется    |
| запись потеряна                         | отказы движка + названная дверью причина; путь восстановления работает |
| запись битая                            | отказ `manifest-unreadable` — кодом движка, а не «что-то не так»       |
| ПЕРВАЯ УСТАНОВКА в непустой репозиторий | `first-install`: файл человека цел, оба выхода работают                |
| пустой репозиторий (записи тоже нет)    | молчит: отсутствие записи здесь норма, а не потеря                     |

**Отдельно — приёмка ручной выдачи, и она про «унесли и заработало», а не про
«собралось».** Бандл копируется в сторону от монорепы и запускается ОТДЕЛЬНЫМ
процессом в чистом чужом репозитории:

| проба                           | что обязано произойти                                         |
| ------------------------------- | ------------------------------------------------------------- |
| чистый чужой репозиторий        | одна команда — обвес разложен, второй прогон сходится         |
| сухой прогон                    | в репозиторий не пишется ничего; тронут только `node_modules` |
| weber: свой `devcontainer.json` | отказ `first-install`, файл цел; `--confirm` снимает          |
| состав установки                | обвес в `node_modules`, а в `dependencies` — на время прогона |
| ссылки на монорепу              | в бандле нет ни одной: он не знает, где его собирали          |

Оба дефекта этой работы статикой не видны вовсе и найдены именно прогоном:
установщик искал опись на уровень выше (писался под раскладку в пакете, а поехал
в бандл), и копирование обвеса оказалось половиной установки. Собиралось
зелёным, падало у человека.

Приёмка бандла идёт по `dist`, поэтому требует собранного пакета — проба
говорит об этом текстом, а не пропускается молча. Изоляцию от монорепы
дополнительно прогоняли руками: `node_modules` монорепы переименован, бандл
разложил обвес в чистый репозиторий как ни в чём не бывало.

**И отдельно — первые пять минут человека, где спрашивают среду, а не код**
(`first-five-minutes.spec.ts`). Каждая проба здесь задаёт вопрос, на который
сборка не отвечает в принципе:

| проба                           | что обязано произойти                                                |
| ------------------------------- | -------------------------------------------------------------------- |
| дорога до потребителя (`tar`)   | бит пережил архив; `./install.mjs` запускается БЕЗ `node` в строке   |
| шебанг ↔ бит                   | обещание симметрично: нет одного без другого                         |
| хост без Node (`PATH` без него) | предусловие настоящее — оттого докерная команда и стоит первой       |
| команда ИЗ ДОКИ                 | разбирается из `INSTALL.md` и исполняется, а не вычитывается глазами |
| чужой репозиторий, `git status` | после `--plan` пусто; после установки — только то, что коммитят      |
| репозиторий без `package.json`  | создали на прогон — снесли целиком, чужеродного файла не осталось    |
| отказ двери (`first-install`)   | манифест всё равно возвращён побайтово                               |
| дверь ПОСЛЕ уборки              | обвес виден: авторитетен `baser.json`, а он остаётся                 |

`git status` здесь не метафора: репозиторий проб — настоящий `git init` с
коммитом, потому что вопрос «что человек увидит перед коммитом» другим способом
не задаётся.

Руками, поверх проб, прогнано то, чего тест не покажет: бандл собран, унесён
`tar`'ом, распакован в стороне и запущен ПРЯМЫМ вызовом в двух живых
репозиториях — weber-подобном (со своим `devcontainer.json`) и Go-репозитории
без `package.json` вовсе. Докерная оболочка из `INSTALL.md` в этот прогон не
входила: в девбоксе докера нет (проверено), а её содержимое — путь до
установщика, рабочий каталог, отсутствие `--cwd` — проба исполняет, разобрав
команду из самой доки.

## Публичная поверхность

| Экспорт                                          | Что                                                  |
| ------------------------------------------------ | ---------------------------------------------------- |
| `run` · `RunOptions`                             | прогон целиком: от конфига до сброса на диск         |
| `cli` · `USAGE` · `CliOutcome`                   | разбор вызова поверх `run`; решений не принимает     |
| `DoorResult` · `DoorStatus` · `exitCodeOf`       | форма ответа и код возврата как её производная       |
| `renderText`                                     | текстовый рендер поверх ответа — один из выходов     |
| `resolveValues` · `SettingMovement`              | значения и движение дефолта                          |
| `renderLayout` · `createDoorSource`              | подстановка и порт содержимого для движка            |
| `readConsumerConfig` · `serializeConsumerConfig` | чтение и рождение конфига потребителя                |
| `resolveInstalledPackage` · `locateContentRoot`  | поставленный обвес и шов `contentRoot`               |
| `bundle` · `BundleReport`                        | сборка запускаемого бандла из нагрузки `pack`        |
| `renderCheck` · `renderPack` · `renderBundle`    | текст поверх ответов механик подготовки              |
| `createRepoTree` · `RepoTree`                    | виртуальное дерево над реальной ФС — порт для движка |
| `DOOR_SCHEMA_VERSION` · `DoorProblemCode`        | версия формы ответа и коды отказов двери             |

Дверь зовут не только из терминала: `run()` — программный вход для гейта,
скрипта и — дальше — пульта, а `cli()` поверх него тонкая ровно настолько, чтобы
разбор argv не был местом, где принимаются решения.
