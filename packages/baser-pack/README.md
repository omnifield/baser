# `@omnifield/baser-pack` — проверенный обвес к выдаче

**Одно обещание: «проверенный обвес, нормализованный и с манифестом выдачи».**
На вход — каталог обвеса, на выход — полезная нагрузка, готовая к любому
способу доставки, и опись рядом с ней.

> Обвес, не подходящий посадочному месту, упаковываться не должен: иначе мы
> выдаём заведомо не встающий обвес и узнаём об этом у потребителя
> (`kb:BASER2-9`).

> **Словарь.** Деталь — это то, что станок ПРОИЗВОДИТ, то есть сам продукт;
> обвес подходит **посадочному месту**, из которых патрон лишь одно
> (`kb:BASER2-4`). Прежняя пара слов («деталь подходит патрону») была
> расхождением внутри канона, а не самодеятельностью зоны; канон поправлен
> 2026-07-29 (`kb:BASER2-9`), зона приведена следом за ним — как и соседняя
> `check`, тексты которой человек видит подряд с этими.

Второе звено цепи `check → pack → выдача` (`tasker:BASER2-29`, задача
`tasker:BASER2-31`).

## Подготовка ≠ доставка

```
проверить  →  собрать  →  вынести
  check        pack        способов много
```

Собрать — всегда одно и то же. Вынести можно папкой в руках, в реестр, в
локальный том. Поэтому здесь **нет ни одного способа доставки**: упаковка ничего
никуда не отправляет, ничего не публикует и не знает, что случится с нагрузкой
дальше. Ручная папка сегодня и публикация завтра — два потребителя одного
выхода, а не два разных флоу.

По той же причине упаковка **не вкладывает в нагрузку дверь**. Вложить себя
может только сама дверь: она единственная знает, из чего состоит. Иначе
упаковка зависела бы от двери, а дверь от упаковки — круг. Направление цепи:
`contracts ← check ← pack ← дверь`.

## Вход и выход

```ts
import { packPackage } from '@omnifield/baser-pack';

const packed = packPackage('packages/baser-devbox', { into: 'tmp/выдача' });
if (!packed.ok) {
  // packed.problems — причины, пришедшие снизу как есть
}
```

```
tmp/выдача/payload/       ← нагрузка: ровно то, что получит потребитель
tmp/выдача/payload.json   ← опись выдачи
```

Опись лежит **рядом**, а не внутри: нагрузку публикуют в реестр и уносят папкой
как есть, и лишний файл в ней менял бы саму нагрузку ради разговора о ней.

Каталог выдачи создаётся сам; непустой — отказ. Молча затирать чужое упаковка
не станет, а разбирать, что там лежало, — не её работа.

## Шесть шагов

| Шаг        | Что делает                                                        |
| ---------- | ----------------------------------------------------------------- |
| `check`    | зовёт `baser-check` по исходному каталогу — иначе не пакует вовсе |
| `target`   | место выдачи: не внутри обвеса, не занято, создаётся              |
| `contents` | состав поставки — **перечислен npm**, а не предсказан             |
| `payload`  | состав скопирован в нагрузку, отпечаток снят с легшего файла      |
| `verify`   | собранная нагрузка проверена заново, как чужой каталог обвеса     |
| `manifest` | опись выдачи написана рядом с нагрузкой                           |

## Состав поставки спрашивается, а не вычисляется

Что именно уедет потребителю, решают `files`, `.npmignore` и встроенные правила
npm вместе. Переписывать эту семантику к себе значило бы завести вторую правду
об упаковке — ту самую, от которой проверка отказалась вслух. Поэтому состав
**запрашивается**: `npm pack --dry-run --json` перечисляет ровно те файлы,
которые попали бы в тарбол, не создавая ни тарбола, ни архива.

Нагрузка при этом — каталог, а не архив: его публикуют, уносят папкой, кладут в
том. Тарбол пришлось бы вскрывать, а вскрытие требует внешнего `tar` там, где
хватает `node:fs`.

## Проверок две, и вторая не выводится из первой

Первая отвечает «стоит ли вообще паковать». Вторая — «годно ли то, что
собралось». Между ними стоит npm со своими правилами упаковки, и каталог
разработчика с поставкой расходятся молча.

Пример, который проба держит живым: **модуль резолвера подменён символической
ссылкой**. Файл открывается, белый список его перечисляет, проверка исходного
каталога чиста — а npm символические ссылки в поставку не увозит, и у
потребителя вычислять дефолт нечем. Увидеть это можно только на собранном.

## Третье состояние: решение названо вслух

Проверка умеет отвечать **`undecidable`** — «не могу сказать»: отрицание или
класс в `files` она не судит, чтобы не заводить вторую правду об упаковке npm.
Это не «годен» и не «негоден».

**Упаковка на это состояние не отказывает — и не проглатывает его.** Она
отвечает на него не более умным разбором, а **сменой источника ответа**: тот же
вопрос задан самому npm, и дальше собранное измерено. Файл, не доехавший из-за
отрицания в `files`, вторая проверка называет пропавшим — и выдавать становится
нечего.

Отказать наглухо значило бы запретить упаковку из-за конструкции, которую мы
просто не разбираем. Паковать молча — выдать обвес, про который мы не знаем,
что в нём. Здесь не сделано ни того, ни другого: неопределённость **снята**, а
не выбрана стороной.

Состояние при этом доезжает до получателя нагрузки:

```json
"shipping": {
  "claim": "undecidable",
  "reason": "в \"files\" есть отрицание (\"!template/**\"): что оно вычитает из состава, решает npm, а не эта проверка",
  "decidedBy": "npm"
}
```

`claim` — что сказала проверка про исходный обвес. `decidedBy` — кто определил
состав нагрузки на самом деле. Полный вердикт проверки лежит в описи целиком, со
всеми пропусками и их причинами.

## Манифест выдачи

Достаточно, чтобы принимающая сторона могла сказать, ЧТО она получила, не
разбирая содержимое заново:

```json
{
  "payloadSchemaVersion": 1,
  "formVersion": 2,
  "source": {
    "id": "omnifield/devbox",
    "title": "Девбокс: проект целиком в контейнере",
    "package": { "name": "@omnifield/baser-devbox", "version": "…" }
  },
  "shipping": { "claim": "declared", "decidedBy": "npm" },
  "artifacts": [
    {
      "dest": ".devcontainer/devcontainer.json",
      "from": "template/devcontainer.json.ejs",
      "render": true
    }
  ],
  "files": [{ "path": "defaults.mjs", "bytes": 5304, "sha256": "…" }],
  "digest": "sha256:…",
  "verified": {
    "checkSchemaVersion": 1,
    "source": { "ok": true, "stages": ["…"] },
    "payload": { "ok": true, "stages": ["…"] }
  }
}
```

`source.id` — личность обвеса, а не имя npm-пакета: пакет это доставка.
`version` — та, что обвес объявил у себя: упаковка её не сочиняет и не хранит,
а переносит из объявления в опись (потому в примере она многоточием — числа тут
не бывает постоянного). `artifacts` — что обвес положит потребителю. `digest`
называет всю нагрузку одним словом. `verified` несёт **оба** вердикта проверки
целиком: по исходному каталогу и по собранной нагрузке, со всеми слоями,
пропусками и их причинами.

> **`formVersion` в цепочке значит два разных предмета — читайте адрес, а не
> имя.** Здесь, в описи выдачи, это версия формы, которую объявил **сам обвес**
> (`declaration.formVersion`, перенесённая из его `package.json` как есть). У
> соседнего звена, в ответе `baser-check`, поле с тем же именем — версия,
> которую поддерживает **проверяющий**, то есть ЭТОТ baser. Имена совпали, а
> предметы нет, и в цепочке `check → pack` эти поля лежат рядом. Поэтому в
> примере выше стоит `2`: столько объявляет живой девбокс, а не столько
> поддерживает baser.

**Это опись груза, а не второй экземпляр груза.** Правда об обвесе живёт в его
`package.json` внутри нагрузки; опись описывает уже замороженный груз и
разойтись с ним молча не может: изменившийся файл меняет отпечаток, и
расхождение видно арифметикой, а не спором двух источников. Переименование файла
меняет отпечаток так же, как правка содержимого.

## Отказ

**Чужой отказ едет как есть.** Когда обвес не годен, `problems` — это ровно
`problems` проверки: тот же код, тот же адрес, тот же текст. Своего «обвес
непригоден» упаковка поверх не пишет: две правды об одном событии это два
события для читателя, и починок у него станет две вместо одной.

Свои коды — только про то, чего проверка сказать не может, потому что она ничего
не пишет и не собирает:

| Код                            | Что случилось                         |
| ------------------------------ | ------------------------------------- |
| `payload-target-occupied`      | в каталоге выдачи уже что-то лежит    |
| `payload-target-inside-source` | каталог выдачи внутри каталога обвеса |
| `payload-target-unwritable`    | каталог выдачи не создать             |
| `contents-unlistable`          | состав поставки не перечислен         |
| `payload-file-uncopyable`      | файл состава не лёг в нагрузку        |
| `manifest-unwritable`          | опись не записать                     |

**После отказа на диске не остаётся ничего, что можно принять за готовую
выдачу.** Всё,
что упаковка успела положить, она за собой убирает — включая нагрузку, которую
не приняла вторая проверка. Полусобранная нагрузка выглядит как настоящая ровно
до того, как её кто-нибудь понесёт. Чужой пустой каталог выдачи при этом остаётся
на месте: убирается только то, что создано своими руками.

`stages` называет объём сделанного и причину каждого пропуска — по той же
причине, что и у проверки: зелёная сборка, которая ничего не собрала, читается
как успешная.

## Чего здесь нет намеренно

- **Доставки.** Ни публикации, ни архива, ни копирования в чужой репозиторий.
  Упаковка не знает способа выдачи и не должна узнать.
- **Двери внутри нагрузки.** Запускаемую папку собирает дверь: вложить себя
  может только она сама (`tasker:BASER2-29`).
- **Второго разбора формы.** Объявление разбирают контракты, пригодность судит
  проверка; сюда приезжает уже разобранное.
- **Второго разбора упаковки npm.** Состав спрашивается у того, кто пакет
  собирает.
- **Рендера шаблонов.** Нагрузка везёт обвес как есть; подстановку делает
  движок при установке.
- **Текстового ответа человеку.** Ответ — данные; текст поверх них печатает
  дверь.

## Почему это пакет, а не обёртка

Правило приёмки то же, что было у `check`: пакет оправдан своей логикой и своими
тестами, а не реэкспортом соседа. Разбор честный:

- `src/index.ts` **не реэкспортирует ни одного символа** `baser-check` или
  `baser-contracts` — наружу выходит только своё;
- из шести шагов вызовами соседа являются два (`check`, `verify`), и оба —
  вызовы **одной и той же** функции по двум разным каталогам. Собственно
  упаковкой заняты остальные четыре;
- ни один из четырёх не мог бы жить у соседа: проверка ничего не пишет и не
  собирает, а начав — перестала бы быть проверкой ровно так же, как контракты
  перестали бы быть формой, получив файловую систему;
- главное, что не сводится ни к кому, — **последовательность и её инварианты**:
  негодное не пакуется, собранное меряется заново, отказ не оставляет следов,
  состав закрыт списком, «не могу сказать» доезжает до получателя.

Двадцатью строками поверх соседа это не оказалось.

## Проба

```
npx vitest run --config packages/baser-pack/vitest.config.mts
```

Приёмка идёт на **живом `packages/baser-devbox`** — том обвесе, который мы
выпускаем сами. Состав нагрузки закрыт **списком, написанным руками**: сверка
выхода с самим собой всегда зелёная, а появившийся в обвесе файл обязан заставить
человека назвать его вслух. Опись сверяется с диском, а не с собой: отпечаток
каждого файла берётся заново с того, что легло.

Главная проба — про **замысел**, а не про код: собранная нагрузка сверяется
**байт в байт с настоящим тарболом** `npm pack`. Всё остальное проверяет, что
упаковка сделала задуманное; эта — что задумано было верно. Без неё «мы спросили
у npm» осталось бы словами: состав спрашивают одним способом, а увозит он
другим.

Отказы гоняются на копии живого обвеса, сломанной по одному пункту за раз, и
каждый тест требует, чтобы после отказа на диске ничего не осталось.

### Что приёмка утверждает значением, а что формой

Приёмка идёт по живому соседу — и потому обязана различать, что в нём **наше
утверждение**, а что **его имущество**:

| В описи                                 | Как проверяется    | Почему так                                                                                 |
| --------------------------------------- | ------------------ | ------------------------------------------------------------------------------------------ |
| `source.id`, `source.title`, имя пакета | прибитым значением | личность обвеса меняется осознанным решением — поехала, и человек обязан назвать это вслух |
| состав нагрузки, `artifacts`            | прибитым списком   | то же: новый файл или новый артефакт — событие, а не фон                                   |
| `source.package.version`                | **формой**         | номер выпуска меняется каждым релизом соседа и ничего не говорит об упаковке               |

Про версию утверждается ровно то, за что отвечает упаковка: она есть, она
непустая, она совпадает с объявленной самим обвесом (прочитанной оттуда же,
откуда её берёт сборка) и с той, что реально уехала в нагрузке. Отдельная проба
пакует **копию обвеса с поднятой версией** и требует, чтобы приёмка осталась
зелёной, а номер в описи приехал новым.

> Прибитый литерал версии однажды уже сделал чужой релизный цикл источником
> красноты в этой зоне (`tasker:BASER2-37`): обвес выпустил `0.3.0`, приёмка
> покраснела, не сломав ничего по существу. **Инвариант, который держит только
> соседняя зона, — не инвариант.**

Проба проверена мутациями — снятый гейт `check`, снятый гейт `verify`, снятая
уборка за отказом, незамеченный непустой каталог выдачи, каталог выдачи внутри
обвеса, `undecidable`, подменённый на «годен», опись внутри нагрузки, отпечаток
без имени файла, ненормализованный порядок описи, путь наружу пакета, размер не
с легшего файла, переупакованный чужой отказ, версия описи, замороженная
литералом вместо объявления, и версия, потерянная по дороге в опись, — **каждая
мутация краснит пробу.**
