# @omnifield/baser-materialize

Ядро материализации baser: **декларация → план → применение → владение**.

Реализует контракт материализации `kb:BASER-5` поверх виртуального дерева Nx
devkit (`Tree`). Рыночное обоснование каждого решения — `kb:BASER-3`; механизм
выбирается по классу файла — `kb:ADR-22`; движок строится на Nx, а не на своём
дереве — `kb:ADR-20`.

Пакет **не содержит реализаций режимов**: `exact` · `merge` · `seed` живут в
зоне `@omnifield/baser-modes` и подключаются через интерфейс стратегии,
опубликованный здесь.

## Модель

```
package.json.omnifield          computePlan()                 applyPlan()
{ contentRoot, frame[] }  ──▶   план (данные, читаемый)  ──▶  запись в Tree
                                 · status (сходимость)          (всё или ничего)
                                 · steps    — что делать
                                 · conflicts — что отклонено
                                 · notices   — что названо
                                 · trace     — спаны прогона
```

Две фазы разделены намеренно: **план читаем до применения** — это инвариант
контракта, а не деталь реализации (рынок подтвердил его дважды независимо:
`nx migrate` разносит план и прогон на две команды, схематики — на две фазы).

### Вывод — данные, текст — рендер поверх

Потребитель материализации — скрипт, CI и панель управления, а не человек в
терминале (`kb:BASER-5`, «Вывод машинночитаем в первую очередь»). Поэтому:

- вид шага (`kind`), причина шага (`reason`), вид конфликта (`kind`) и вид
  извещения — **стабильные машинные коды**; подробности причины лежат данными в
  `detail`. Ветвиться по тексту `message` нельзя ни гейту, ни панели;
- `describePlan` — **один из выходов**, а не источник: он рендерит те же данные;
- план и отчёт несут `schemaVersion` — контракт формы ответа с панелью;
- трейсы — именованные спаны с длительностью и атрибутами (телеметрия), а не
  печать в поток.

### Состояние плана: `status`

| `status`    | Что значит                                   |
| ----------- | -------------------------------------------- |
| `converged` | сошлось: ни шагов, ни конфликтов             |
| `pending`   | есть шаги, конфликтов нет — план применим    |
| `blocked`   | есть конфликты — план не применяется целиком |

**Признак сходимости отделён от признака пустоты намеренно.** План без шагов, но
с конфликтом владения, сходимости не означает; отдельного признака «в плане нет
шагов» в схеме нет, чтобы гейт не мог зазеленеть на нерешённом конфликте
случайно. Применимость — `isApplicable(plan)` (`status !== 'blocked'`).

### Извещения (`notices`)

Состояния, которые обязаны быть **названы**, но не являются ни шагом, ни отказом:

| `kind`             | Когда                                                                |
| ------------------ | -------------------------------------------------------------------- |
| `product-owned`    | `dest` существует, класс владения — `product`: движок его не трогает |
| `baseline-missing` | базы 3-way нет — мердж будет двухсторонним, и это сказано вслух      |

### Декларация

Единственный источник существования артефакта — блок `omnifield` в манифесте
продукта:

```jsonc
{
  "omnifield": {
    "kind": "plugin",
    "target": "repo",
    "stack": "node",
    "contentRoot": "node_modules/@omnifield/preset-kit/content",
    "frame": [
      {
        "src": "ci/build.yml",
        "dest": ".github/workflows/build.yml",
        "mode": "exact",
      },
    ],
  },
}
```

Общего `mechanism` у декларации нет: механизм несёт каждая запись `frame`
отдельно. Движок валидирует то, чем пользуется (`contentRoot`, `frame`), прочие
поля блока сохраняет в `declaration.extra` без интерпретации.

Вендор-ветка доставки (`plugin.json`) сознательно **не поддерживается**: это
обходной путь потребителя, а не форма канона (`kb:BASER-3`, `kb:BASER-4`).

### Владение

Единица владения — файл `dest`. Принадлежность **не хранится реестром** (реестр
рассинхронизируется сам — анти-паттерн `kb:BASER-3`), а выводится из содержимого
по маркеру, который движок ставит в артефакт:

```yaml
# ~~ Generated by @omnifield/baser-materialize ~~ ручные правки не сохраняются — правь декларацию ~~ {"src":"ci/build.yml","mode":"exact","own":"engine","version":"1.4.0"}
name: build
```

Класс владения объявляет стратегия режима, а движок его **защищает**:

| Класс     | Прототип | Существующий чужой `dest`         | Запись убрана из `frame`          |
| --------- | -------- | --------------------------------- | --------------------------------- |
| `engine`  | `exact`  | отказ (конфликт `foreign-dest`)   | артефакт снимается                |
| `shared`  | `merge`  | берётся во владение (`adopted`)   | снимается только маркер-претензия |
| `product` | `seed`   | не трогается — **шага нет вовсе** | ничего (файл продукта)            |

Отпускание владения для `shared` — прямой перенос семантики Kubernetes SSA:
убрали претензию, значение осталось владельцу.

**Маркер утверждает ТЕКУЩЕЕ объявленное владение, а не историю** (`kb:BASER-5`).
Отсюда поведение на смене декларации: если `dest` несёт наш маркер, а запись
`frame` теперь объявляет его классом `product`, движок снимает претензию шагом
`release` (причина `reclaimed`) — той же семантикой, что у осиротевшего
`shared`. Оставить маркер нельзя: артефакт продолжал бы утверждать снятое
владение, и следующее снятие записи из `frame` удалило бы файл продукта вместе с
его правками. Расхождение маркера с декларацией — **не сходимость**. Извещение
`product-owned` остаётся для случая, когда маркера нет.

**Границы держит движок, а не добросовестность режима** (`kb:BASER-5`, «Что
движок обязан защищать сам»). Инвариант, который держит только стратегия, — не
инвариант: стратегии приходят из зоны `baser-modes` и пишутся разными сессиями.
Поэтому:

- существующий `dest` класса `product` **не порождает шага, что бы ни вернула
  стратегия** — её для такого файла даже не спрашивают, и `force` этого не
  меняет (`seed` однократен по инварианту движка, а не по договорённости);
- первичное взятие непомеченного файла во владение — **отдельное событие**:
  причина шага `adopted`, а не `diverged`. «Файл разошёлся с каноном» и «файл
  впервые взят под управление» гейт обязан показывать по-разному. Для `shared`
  это штатный путь, для `engine` — только под явным `force`.

Классы файлов, которые не могут нести маркер (нет синтаксиса комментария, JSON
без объекта в корне), движок **во владение не берёт**: он отказывает с
сообщением, а не молча перезаписывает. Поддержаны `#`-комментарии
(yaml/toml/sh/`Dockerfile`/`.gitignore`/…), `//` (ts/js/css/jsonc), `<!-- -->`
(md/html/xml) и ключ `"//"` для JSON. Пролог файла (`#!`, `<?xml`, `<!doctype`)
остаётся первой строкой.

### Причины шага (`reason`)

| `reason`    | Событие                                                         |
| ----------- | --------------------------------------------------------------- |
| `missing`   | объявленного артефакта нет — материализуем впервые              |
| `diverged`  | тело артефакта под нашим маркером разошлось с каноном           |
| `adopted`   | существовавший непомеченный файл впервые взят во владение       |
| `reclaimed` | сменилось объявленное владение — маркер приводится к декларации |
| `orphan`    | артефакт потерял объявление в `frame`                           |

Порядок причин значим: если декларация сменила claim (`src` · `mode` · класс),
первичное событие — именно это, а не сопутствующее ему расхождение тела. Причина
шага — часть машинного контракта и обязана быть правдой: на неё ветвятся гейт и
панель.

### Что считается расхождением

Сравнение «сошлось / разошлось» ведётся по **телу артефакта** и по
**актуальности претензии**, а не по строке маркера целиком:

- **версия канона — провенанс, а не основание для шага.** Бамп версии при том же
  теле не порождает ничего: иначе каждый релиз канона переписывал бы все
  артефакты у всех потребителей, настоящий дрейф утонул бы в этом шуме, а гейт
  рапортовал бы расхождение там, где ничего не разошлось. Версия в маркере
  обновляется вместе с телом, когда шаг и так происходит;
- **claim обязан отражать декларацию** — устаревший маркер утверждает снятое
  владение (см. выше).

База мерджа от этого не страдает: если тело между версиями не менялось,
содержимое `src` в записанной версии и есть корректная база.

### База трёхстороннего мерджа

База **не хранится копией и не заводит файла состояния** (это был бы тот самый
реестр — анти-паттерн `kb:BASER-3`). Маркер несёт **версию канона**, из которой
артефакт материализован; база = содержимое `src` в той версии источника, и
восстанавливает её сторона, знающая версии пакетов (раннер/гейт), через порт
`CanonBaseline.read(src, version)`. Версию для новых артефактов подаёт
`CanonSource.version`.

Базы нет → мердж **не трёхсторонний**, и план это НАЗЫВАЕТ извещением
`baseline-missing` (`detail.cause`: `no-version` — артефакт версии не несёт;
`unresolved` — версия известна, но источник базы её не отдал), а не вырождается
в двухсторонний молча.

### Конфликт — отказ, а не перезапись

Конфликты попадают в `plan.conflicts` (план остаётся читаемым целиком) и делают
план неприменимым (`status: 'blocked'`): `applyPlan` бросает
`MaterializationConflictError` и **не применяет ничего**. Перезапись поверх
чужого владения — отдельное явное действие: `computePlan({ force: true })`
(семантика `--force-conflicts` из SSA). Каждый конфликт несёт машинный `kind` и
`detail` (`claimedBy` · `sourcePath` · `availableModes` · `resolution` ·
`unmarkable` · `strategyReason`) — `message` дублирует их для человека, но
единственным носителем причины не является.

## Использование

```ts
import {
  applyPlan,
  computePlan,
  describePlan,
  readDeclaration,
} from '@omnifield/baser-materialize';
import { modeStrategies } from '@omnifield/baser-modes'; // режимы — соседняя зона

export default async function (tree: Tree) {
  const declaration = readDeclaration(tree);
  const plan = computePlan({ tree, declaration, strategies: modeStrategies });

  // Решение принимается по КОДУ, не по тексту: текст — рендер для человека.
  if (plan.status === 'blocked') {
    return { plan, rendered: describePlan(plan) }; // причины — в plan.conflicts
  }
  if (plan.status === 'converged') {
    return { plan };
  }

  const report = applyPlan(tree, plan); // бросит, если есть конфликты владения
  return { plan, report }; // report.trace — спаны прогона для мониторинга
}
```

Полный результат любой операции доступен **данными**: `plan` и `report`
сериализуются как есть, парсить текст не нужно ни разу.

**Запись в реальную ФС — не эта зона.** Движок работает только с `Tree`; сброс
изменений на диск делает раннер (Nx-генератор сбрасывает дерево сам). Отсюда и
атомарность: применение либо проходит целиком, либо дерево откатывается
журналом отката и остаётся в исходном состоянии.

### Шов: интерфейс стратегии

Стратегия отвечает на один вопрос — каким должно быть содержимое `dest`, — и
**не пишет в дерево**: решение применяет движок, он же ставит маркер владения и
держит инварианты.

```ts
interface MaterializationStrategy {
  readonly mode: 'exact' | 'merge' | 'seed';
  readonly ownership: 'engine' | 'shared' | 'product';
  decide(input: StrategyInput): StrategyDecision;
}

// StrategyInput:  entry · declaration · source · current (без маркера) · baseline · owned · record
// StrategyDecision: { kind: 'write', content } | { kind: 'keep' } | { kind: 'conflict', reason }
```

Форма опубликована: менять её после публикации — только через architect (это
контракт между двумя зонами).

## Трейсы

`plan.trace` и `report.trace` несут спаны с длительностями (`plan.frame`,
`plan.scan-ownership`, `plan.owned`, `plan.orphans`, `apply.steps`,
`apply.rollback`). Скан владения — проход по дереву на каждый прогон:
корректность↑, скорость↓, размен осознанный и измеряемый (`kb:BASER-3`). Трейс
никогда не попадает в содержимое артефактов — иначе таймстемпы сломали бы
идемпотентность.

## Известные ограничения

- **Гранулярность владения — файл.** Для `merge`-конфигов совместного вклада это
  грубо; рынок умеет по полю (SSA `managedFields`). Ограничение зафиксировано
  контрактом осознанно.
- **База 3-way-мерджа резолвится не движком.** Движок записывает версию канона в
  маркер и спрашивает базу через порт; хранением версий и их выдачей занимается
  раннер. Без него мердж двухсторонний — и план это называет.
- **Неразмечаемые классы файлов** нельзя взять во владение (см. выше). Контракт
  запрещает объявлять такие `dest` с режимами класса `engine`/`shared` — отказ
  движка в рантайме остаётся второй линией, а не единственной.
- `align` (принять правку потребителя в канон) движком не автоматизируется: он
  лишь показывает расхождение через `step.previous` — решение за архитектором.

## Тесты

```
nx test @omnifield/baser-materialize
```

Unit на мок-дереве (`createTreeWithEmptyWorkspace`) + снапшоты выходных файлов —
канон тестирования генераторов (`kb:BASER-3`). Покрыты все приёмочные инварианты
контракта: идемпотентность (второй прогон = `status: 'converged'`), атомарность
(сбой в середине не оставляет полуобновлённого дерева), сироты, конфликт
владения, отделение сходимости от пустоты, машинночитаемость вывода.

**`transitions.spec.ts` — матрица переходов** (`kb:BASER-5`, «Контракт
проверяется ПЕРЕХОДАМИ, а не устойчивыми состояниями»): по одному `describe` на
строку матрицы контракта. Это не дубль статических тестов — оба дефекта второго
ревью лежали именно в переходах, а в устойчивом состоянии всё сходилось с
первого раза. Отдельно проверена цепочка `exact` → `seed` → правка продукта →
снятие записи: файл продукта обязан пережить её целиком вместе с правками.

Стратегии в тестах — двойники (`strategies.fixture.ts`), по одному на класс
владения: зона проверяет инварианты движка, не завися от `baser-modes`. Среди
них есть **небрежный** двойник (`CARELESS_DOUBLES`): инварианты границ проверяются
злоупотреблением швом, а не корректным двойником — проверять корректной
стратегией то, что движок обязан защищать сам, значит не проверять вовсе.
