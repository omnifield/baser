# @omnifield/baser-materialize

Ядро материализации baser: **декларация → план → применение → владение**.

Движок раскладывает объявленные шаблоны по репозиторию и потом их обновляет
(`kb:BASER2-2`). Про содержимое он не знает ничего — только «вот шаблон, вот
куда класть». По форме — генератор Nx поверх виртуального дерева devkit (`Tree`).

## Единственное поведение: перегенерация целиком

**Объявленный артефакт — наш, и при каждом обновлении он перегенерируется из
шаблона целиком.** Это модель A по `kb:BASER2-1`.

**Сведения версий файла нет ни в каком виде.** Движок никогда не сводит
исходную, пользовательскую и новую версию — ни под каким флагом. Отсюда, чего в
этой зоне НЕТ и не появится без смены канона:

| Снято                                          | Почему                                                      |
| ---------------------------------------------- | ----------------------------------------------------------- |
| режимы `exact` · `merge` · `seed`               | поведение одно, выбирать нечего                             |
| поле `layout[].mode` в декларации                | объявлять нечего; поле отвергается вслух, а не игнорируется |
| шов стратегий (`MaterializationStrategy`)       | развилки по режиму нет                                      |
| классы владения `engine`/`shared`/`product`     | владелец объявленного артефакта ровно один — движок         |
| порт базы 3-way (`CanonBaseline`) и версия канона  | третьей стороны сведения не существует                 |

**Правка руками — флаг, а не переход владения.** Правка нашего артефакта не
делает файл пользовательским: следующий прогон его перегенерирует. Затирание
само по себе не дефект — дефектом было молчание, поэтому план несёт прежнее
содержимое в `step.previous` и называет потери ДО применения.

**Владение продукта выражается форком источника** — целиком, снаружи движка
(единица форка — источник, не файл). Рыночный прототип — `eject` у CRA: покрытая
настройка для типового плюс названная вслух дверь наружу.

## Модель

```
дверь собирает вход             computePlan()                 applyPlan()
{ source, layout[] }      ──▶   план (данные, читаемый)  ──▶  запись в Tree
                                 · status (сходимость)          (всё или ничего)
                                 · steps    — что делать
                                 · conflicts — что отклонено
                                 · notices   — что названо
                                 · trace     — спаны прогона
```

**Движок ничего не читает сам.** Настоящая декларация размазана по двум файлам в
разных пакетах — объявление обвеса (`package.json.baser` пакета-поставщика) и
конфиг потребителя (`baser.json` в его репозитории), — и склеить их может только
дверь: у неё есть и то, и другое, и разрешение значений настроек
(`packages/baser-contracts/README.md`, `kb:BASER2-5`). Знание про манифест —
знание двери, а не станка, поэтому чтения декларации в этой зоне нет.

Две фазы разделены намеренно: **план читаем до применения** — это инвариант, а
не деталь реализации (рынок подтвердил его дважды независимо: `nx migrate`
разносит план и прогон на две команды, схематики — на две фазы).

### Вывод — данные, текст — рендер поверх

Потребитель материализации — скрипт, CI и пульт, а не человек в терминале.
Поэтому:

- вид шага (`kind`), причина шага (`reason`), вид конфликта (`kind`) и вид
  извещения — **стабильные машинные коды**; подробности причины лежат данными в
  `detail`. Ветвиться по тексту `message` нельзя ни гейту, ни панели;
- `describePlan` — **один из выходов**, а не источник: он рендерит те же данные;
- план и отчёт несут `schemaVersion` — контракт формы ответа с пультом;
- трейсы — именованные спаны с длительностью и атрибутами (телеметрия), а не
  печать в поток.

`OUTPUT_SCHEMA_VERSION` = **4**. Версия 2 сняла с вывода мердж; версия 3 —
переход на словарь контракта (`frame` → `layout`, `contentRoot` →
`source.contentRoot`); версия 4 — переезд служебной записи в манифест сбоку:
план и отчёт несут `manifestPath` и `manifest`, у шага появились вид `record` и
поле `record`, сняты конфликт `unmarkable-dest` и извещение
`scan-scope-narrowed` вместе со сканом дерева. Потребитель, ветвившийся по
снятым кодам или читавший владение из содержимого артефакта, обязан это
увидеть, а не молча промахнуться.

### Состояние плана: `status`

| `status`    | Что значит                                   |
| ----------- | -------------------------------------------- |
| `converged` | сошлось: ни шагов, ни конфликтов             |
| `pending`   | есть шаги, конфликтов нет — план применим    |
| `blocked`   | есть конфликты — план не применяется целиком |

**Признак сходимости отделён от признака пустоты намеренно.** План без шагов, но
с конфликтом владения, сходимости не означает; отдельного признака «в плане нет
шагов» в схеме нет, чтобы гейт не мог зазеленеть на нерешённом конфликте
случайно. Применимость — `isApplicable(plan)` (`status !== 'blocked'`).

### Вход: готовая структура

Единственный источник существования артефакта — запись `layout`, поданная
дверью:

```ts
const declaration: Declaration = {
  source: {
    id: 'omnifield/devbox', // идентичность обвеса, не имя npm-пакета
    contentRoot: 'node_modules/@omnifield/baser-devbox/template',
  },
  layout: [{ src: 'devcontainer.json', dest: '.devcontainer/devcontainer.json' }],
};
```

Словарь общий с контрактом (`packages/baser-contracts`): `source` · `layout` ·
`src` · `dest`. Двух языков на один предмет не держим.

Запись `layout` — это пара «шаблон → артефакт», и больше ничего. Режимов в ней
нет и интерпретировать их некому: `merge` отменён вместе со сведением версий,
`seed` выражается форком источника. Посторонние поля записи движок не читает —
отвергает их разбор формы, а это зона контрактов.

`source.id` движок не интерпретирует и в артефакты не пишет (запись владения —
A2, `tasker:BASER2-4`): он часть общего словаря, на котором говорят все три
зоны — движок, дверь и обвес.

**Настроек и пресетов во входе нет.** Значения разрешает дверь, а подставляет их
в содержимое тот, кто отдаёт движку шаблон, — порт `CanonSource`. Движок
получает содержимое уже готовым и кладёт его целиком, поэтому «куда настройка
попадает внутри артефакта» остаётся делом обвеса (`kb:BASER2-5`).

### Годность входа против разбора формы

Форму декларации разбирает дверь. Движок проверяет не форму, а **пригодность
входа для собственной работы**, и делает это сам — инвариант, который держит
только соседняя зона, не инвариант:

| Что                                             | Ответ движка                          |
| ----------------------------------------------- | -------------------------------------- |
| нет `layout` / не массив, нет `source.contentRoot` | `DeclarationError` — плана нет и быть не может |
| `contentRoot` вырожден (`.`, `/`, пусто)        | `DeclarationError` — источником стало бы всё дерево, и прогон затирал бы шаблоны, из которых читает |
| путь записи пуст, абсолютен или с `..`          | конфликт `invalid-path` по своей записи, соседние планируются |

Разница намеренная: без раскладки и корня содержимого план построить не из чего
(исключение), а одна кривая запись не имеет права уносить прогон (отказ в плане).
Пути приводятся к каноничной форме здесь же: движок сверяет объявленный `dest` с
путями из скана владения, и разъехавшись в написании (`./a.yml` против `a.yml`),
свежесозданный артефакт оказался бы сиротой сам себе.

Движок валидирует то, чем пользуется (`contentRoot`, `layout`), прочие поля блока
сохраняет в `declaration.extra` без интерпретации. Вендор-ветка доставки
(`plugin.json`) сознательно **не поддерживается**: это обходной путь
потребителя, а не форма канона.

### Владение: манифест сбоку

Единица владения — файл `dest`, а **принадлежность выводится из служебной записи
в манифесте**, который лежит СБОКУ от артефактов (`baser.lock.json` рядом с
конфигом потребителя). Внутрь файлов движок не пишет ничего:

```jsonc
// baser.lock.json — служебная запись движка, коммитится вместе с артефактами
{
  "version": 1,
  "artifacts": [
    {
      "dest": ".devcontainer/devcontainer.json",
      "src": "devcontainer.json",
      "source": "omnifield/devbox",
      "hash": "sha256:2f0e…"
    }
  ]
}
```

Прежняя модель доказывала владение наклейкой ВНУТРИ артефакта, и это упёрлось
трижды (`tasker:BASER2-4`):

| Было с наклейкой                                        | Стало с записью сбоку                     |
| ------------------------------------------------------- | ------------------------------------------ |
| JSONC и бинарь пометить нечем → `unmarkable-dest`, план блокирован | **класс файла не условие владения**: кладётся что угодно |
| `render: false` не мог лечь байт в байт — маркер вписывался всё равно | **содержимое не трогается вовсе**       |
| наклейка устаревала и врала — файл терялся молча         | запись приводится шагом и **называется**   |

**Содержимое артефакта равно тому, что дал источник, байт в байт.** Отсюда же
следует, что артефакт, переписанный пользователем до неузнаваемости, остаётся
нашим: владение не зависит от содержимого, поэтому правка — это флаг, а не
переход владения, и сиротой такой файл найдётся так же исправно.

| Состояние `dest`                        | Что делает движок                                  |
| --------------------------------------- | --------------------------------------------------- |
| нет файла                               | шаг `create` (`missing`)                            |
| есть запись, содержимое разошлось       | шаг `update` (`diverged`) — перекладываем целиком   |
| есть запись, содержимое целевое, запись устарела | шаг `record` (`reclaimed`) — **файл не трогаем** |
| файл есть, записи нет                   | **отказ** `foreign-dest`; снимается `confirm`       |
| запись есть, объявления в `layout` нет  | шаг `delete` (`orphan`)                             |

**Запись обязана утверждать ровно то, что объявлено СЕЙЧАС** — независимо от
того, совпало содержимое или нет (`tasker:BASER2-16`, Д10). Совпадение
содержимого не повод молчать: устаревшая запись переживает смену объявления и
всплывает потом снятием не того файла. Отсутствие записи — частный случай «не
утверждает». Именно поэтому приведение записи это ШАГ (`record`), а не тихая
правка на применении: план, молчащий о работе, которую всё равно сделает,
рапортует сходимость там, где её нет.

Хеш в записи — хеш того, что положил движок. По нему потребитель отличает
«правили руками» от «уехал шаблон», хотя действие в обоих случаях одно —
перегенерация, и причина шага поэтому одна (`diverged`).

**Манифест не артефакт.** Он не объявляется раскладкой, сиротой не бывает и сам
себя не учитывает; `dest`, равный пути манифеста, — отказ `dest-is-manifest`
(иначе движок писал бы поверх собственной записи, и прогон не сходился бы
никогда). Пустой манифест не остаётся огрызком — файл снимается.

**Битый манифест — отказ, а не «считаем, что записей нет».** Подменить
нечитаемый файл пустым значило бы объявить все свои артефакты чужими: прогон
превратился бы в отказ по каждому `dest` либо, под подтверждением, в перезапись
поверх непонятного состояния.

### Сироты ищутся по записям, а не сканом дерева

Раньше сироты искались проходом по всему дереву в поисках наклейки, и у скана
были и слепые зоны (пропуск каталогов ради скорости), и обратная беда — чужой
файл, случайно похожий на наш. Запись сбоку снимает и то, и другое: **сирота —
это запись, потерявшая объявление**, и никакого охвата у такого поиска нет.
Вместе со сканом ушли `ScanOptions`, извещение `scan-scope-narrowed` и целый
класс дефектов.

### Объявленное состояние обязано быть физически достижимым

Атомарность движка кончается на виртуальном дереве: сброс на реальную ФС делает
раннер, и его сбой происходит **уже вне журнала отката**. Поэтому всё, что упадёт
при записи на диск, ловится ПЛАНОМ — дерево Nx терпит файл и каталог с одним
путём одновременно, файловая система не терпит, и эталон реальности здесь она.

| Что объявлено                         | Конфликт                                               |
| ------------------------------------- | ------------------------------------------------------ |
| `dest` внутри пути другого `dest`     | `unreachable-dest` (`collision: 'declared-dest'`)      |
| родительский путь `dest` занят файлом | `unreachable-dest` (`collision: 'existing-file'`)      |
| путь `dest` занят каталогом           | `unreachable-dest` (`collision: 'existing-directory'`) |
| `dest` внутри `contentRoot`           | `dest-in-content-root`                                 |

Проверки стоят **по существу**, а не побочно: коллизия `cfg` + `cfg/inner.yml`
раньше отбивалась правилом про неразмечаемый класс файла, а `dest` в
`contentRoot` — конфликтом чужого файла. Побочная защита отваливается, как
только меняется смежное правило, поэтому оба случая названы своими кодами.

**Препятствие снимает только собственный шаг удаления.** Путь, занятый нашим же
артефактом, который этот план снимает как сироту, `dest` не перекрывает: иначе
штатная миграция «файл стал каталогом» (`cfg.yml` → `cfg.yml/inner.yml`)
блокировала бы сама себя — план СОДЕРЖИТ снятие мешающего файла и одновременно
объявляет состояние недостижимым, применение отклоняется целиком, следующий
прогон даёт то же самое. Дедлок снимался только руками по ФС.

Правило намеренно узкое: движок **не моделирует гипотетическое дерево** «после
применения», а смотрит на один факт — есть ли в этом плане шаг удаления этого
пути. Файл, который остаётся лежать законно (чужой или по-прежнему объявленный),
продолжает мешать законно.

Порядок применения при этом значим, и его держит `applyPlan`: **сначала снятия,
потом записи**. Порядок в самом плане — байтовый по `dest`, потому что это
контракт вывода с пультом, а не программа действий.

### Причины шага (`reason`)

| `reason`    | Событие                                                       |
| ----------- | ------------------------------------------------------------- |
| `missing`   | объявленного артефакта нет — материализуем впервые            |
| `diverged`  | содержимое разошлось с тем, что даёт источник сейчас         |
| `adopted`   | существовавший файл без записи впервые взят во владение      |
| `reclaimed` | служебная запись разошлась с декларацией — приводится к ней  |
| `orphan`    | запись потеряла объявление в `layout`                        |

Причина шага — часть машинного контракта и обязана быть правдой: на неё
ветвятся гейт и панель. Поэтому `reclaimed` стоит ровно там, где меняется ТОЛЬКО
запись; если разошлось ещё и содержимое, событие для пользователя — потери
(`diverged` с прежним содержимым в `previous`), а запись приводится тем же шагом
и отдельного события не требует.

### Подтверждение адресно, а не глобально

Подтверждение подаётся **перечнем конкретных `dest`**, а не булевым флагом.
Форма «подтвердить всё» отсутствует намеренно: глобальный флаг превращал бы
согласованный escape hatch в оружие по площадям — подтвердив одну перезапись,
потребитель молча усыновлял и переписывал все прочие чужие файлы декларации.

```ts
const plan = computePlan({ tree, declaration });
// план сам называет, что требует подтверждения:
const needsConfirm = plan.conflicts
  .filter((conflict) => conflict.detail.resolution === 'confirm')
  .map((conflict) => conflict.dest);

// подтверждаем ровно то, на что согласны — соседние отказы остаются в силе
computePlan({ tree, declaration, confirm: ['b.yml'] });
```

**Согласие не масштабируется само:** подтверждение одного действия никогда не
подтверждает соседнее, даже однотипное. Подтверждение, которое не понадобилось
(отказа по этому `dest` нет либо он не объявлен), — извещение
`confirmation-unused`, а не молчание.

### Конфликт — отказ, а не перезапись

Конфликты попадают в `plan.conflicts` (план остаётся читаемым целиком) и делают
план неприменимым (`status: 'blocked'`): `applyPlan` бросает
`MaterializationConflictError` и **не применяет ничего**. Каждый конфликт несёт
машинный `kind` (`duplicate-dest` · `foreign-dest` · `unreachable-dest` ·
`dest-in-content-root` · `unmarkable-dest` · `missing-source` · `invalid-path` ·
`entry-failed`) и `detail` (`claimedBy` · `sourcePath` · `resolution` ·
`blockedBy` · `collision` · `contentRoot` · `unmarkable` · `failure` · `field` ·
`path` · `pathProblem`) — `message` дублирует их для человека,
но единственным носителем причины не является.

**Сбой на одной записи не уносит план целиком.** Порт источника и дерево
приходят снаружи движка и могут бросить что угодно; исключение становится
адресным отказом `entry-failed` по своему `dest`, а соседние записи планируются
как обычно. План при этом целиком неприменим — сбой не проглатывается и шагом не
становится. С несколькими источниками (`tasker:BASER2-7`, A5) это уже не
удобство: битый шаблон одного поставщика не должен гасить материализацию всех
остальных.

## Использование

```ts
import {
  applyPlan,
  computePlan,
  describePlan,
} from '@omnifield/baser-materialize';
import type { Declaration } from '@omnifield/baser-materialize';

// declaration собрала ДВЕРЬ: объявление обвеса + конфиг потребителя +
// разрешённые значения настроек. Движок его только читает как структуру.
export default async function (tree: Tree, declaration: Declaration) {
  const plan = computePlan({ tree, declaration });

  // Решение принимается по КОДУ, не по тексту: текст — рендер для человека.
  if (plan.status === 'blocked') {
    return { plan, rendered: describePlan(plan) }; // причины — в plan.conflicts
  }
  if (plan.status === 'converged') {
    return { plan };
  }

  const report = applyPlan(tree, plan); // бросит, если есть конфликты владения
  return { plan, report }; // report.trace — спаны прогона для мониторинга
}
```

Полный результат любой операции доступен **данными**: `plan` и `report`
сериализуются как есть, парсить текст не нужно ни разу.

**Запись в реальную ФС — не эта зона.** Движок работает только с `Tree`; сброс
изменений на диск делает раннер (Nx-генератор сбрасывает дерево сам). Отсюда и
атомарность: применение либо проходит целиком, либо дерево откатывается журналом
отката и остаётся в исходном состоянии.

## Публичная поверхность

| `computePlan` · `describePlan` · `isApplicable`       | фаза плана: `MaterializationPlan`, `PlanStep`, `PlanConflict`, `PlanNotice` |
| `applyPlan`                                           | фаза применения: `ApplyReport`                                              |

## Трейсы

`plan.trace` и `report.trace` несут спаны с длительностями
(`plan.scan-ownership`, `plan.owned`, `plan.layout`, `plan.orphans`,
`apply.steps`, `apply.rollback`). Скан владения — проход по дереву на каждый
прогон: корректность↑, скорость↓, размен осознанный и измеряемый. Трейс никогда
не попадает в содержимое артефактов — иначе таймстемпы сломали бы
идемпотентность.

## Известные ограничения

- **Гранулярность владения — файл.** Единица форка при этом — источник, и
  расхождение между ними закрывается не здесь (форк живёт снаружи движка).
- **Манифест обязан коммититься.** Без него следующий прогон не может доказать
  владение ни одним артефактом и берёт их как чужие: отказ `foreign-dest` по
  каждому `dest`. Это честнее тихой перезаписи, но потребителю надо знать.
- **Порт источника отдаёт строку.** Владение бинарным артефактом запись сбоку
  уже позволяет, а вот прочитать бинарный шаблон через `CanonSource` нельзя —
  расширение порта отдельная работа, не входившая в минимальный A2.
- **Миграции со старой модели нет.** Артефакты, помеченные наклейкой внутри
  файла, записи о себе не имеют и берутся как чужие, пока их не подтвердят
  поимённо. Продукт не выпущен, потребителей за пределами репозитория нет.

## Тесты

```
nx test @omnifield/baser-materialize
```

Unit на мок-дереве (`createTreeWithEmptyWorkspace`) + снапшоты выходных файлов —
канон тестирования генераторов (`kb:BASER-3`). Покрыты приёмочные инварианты:
идемпотентность (второй прогон = `status: 'converged'`), атомарность (сбой в
середине не оставляет полуобновлённого дерева), сироты, конфликт владения,
отделение сходимости от пустоты, машинночитаемость вывода.

**`plan.spec.ts` → «движок принимает готовую структуру»** — приёмка И1.5: план
и применение идут по структуре, поданной снаружи, в дереве без единого
манифеста; чтения декларации в публичной поверхности нет; кривая структура
отвергается внятно, а кривая запись — адресно; файловой системы движок не
касается.

**`plan.spec.ts` → «сведения версий не происходит ни при каком входе»** —
приёмка A1: при любом состоянии существующего артефакта (дописан, урезан,
переписан, пуст, помечен наклейкой прошлой модели) результат равен шаблону
целиком — байт в байт.
Инвариант держится ОТСУТСТВИЕМ механизма, а не поведением по умолчанию, поэтому
там же проверяется, что в публичной поверхности нет ни шва режимов, ни порта
базы.

**`transitions.spec.ts` — матрица переходов**: по одному `describe` на строку.
Это не дубль статических тестов — дефекты обоих ревью лежали именно в переходах,
а в устойчивом состоянии всё сходилось с первого раза.

**`plan.spec.ts` → «владение выводится из манифеста» и «запись обязана
утверждать объявленное сейчас»** — приёмка A2: запись несёт путь, шаблон, обвес
и хеш; класс файла больше не условие владения (JSONC, JSON-массив, бинарь,
`LICENSE`); смена `src` или обвеса при совпавшем содержимом даёт шаг `record`, а
не молчание (Д10); битый манифест — отказ; манифест не может быть целью
раскладки.

Отдельно закрыты дефекты, ПЕРЕЖИВШИЕ выпил мерджа (`tasker:BASER2-16`): дедлок
на переобъявлении файла в каталог (Д11, `transitions.spec.ts`), падение всего
прогона от сбоя одной записи (Д14) и локале-зависимый порядок вывода (нит) — в
`plan.spec.ts`. Д13 (снятие сироты из источника шаблонов) закрылся сам вместе со
сканом: сироты ищутся по записям, и в источник поиск не заходит по построению.
Каждый тест проверен на красноту против кода ДО фикса.
