# `@omnifield/baser-devbox` — обвес девбокса

**Проект целиком в контейнере: `.devcontainer` как шаблон с пресетом.** Первый
настоящий обвес baser — тот, на котором станок впервые что-то положил в живой
репозиторий (`tasker:BASER2-18`, `tasker:BASER2-21`).

Пакет **не содержит кода**: объявление в `package.json`, содержимое в
`template/`, вычисляемые дефолты в `defaults.mjs`. Ни точки входа, ни сборки, ни
`dist` — обвес это инструмент в патроне, а не ещё один мотор (`kb:BASER2-4`).

```
package.json     блок `baser` — объявление обвеса по форме хвостовика
defaults.mjs     резолверы: имя девбокса, алиас в сети, пин версии Node
template/        devcontainer.json.ejs · devcontainer-lock.json
```

## Как им пользуются

```jsonc
// baser.json в корне репозитория
{
  "sources": [{ "use": "@omnifield/baser-devbox", "presets": ["omnifield"] }],
}
```

```
pnpm add -D @omnifield/baser-devbox
npx baser apply
```

**Вопросов не будет ни одного.** Имя девбокса считается из имени репозитория,
всё остальное — дефолты и пресет (`tasker:BASER2-18`). Кладётся два файла:
`.devcontainer/devcontainer.json` и `.devcontainer/devcontainer-lock.json`.

Внешнему пользователю пресет `omnifield` не нужен — без него обвес даёт валидный
самостоятельный девбокс.

## Три слоя, и они не смешиваются

| слой              | что в нём                                                                                                             | чем выражен                     |
| ----------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------- |
| **универсальное** | всё в контейнере · рабочая папка в томе · креды и кэши в отдельных томах · `host.docker.internal` · рестарт с демоном | тело шаблона, без ветвлений     |
| **настройки**     | имя девбокса · образ и версия рантайма · команда установки зависимостей · расширения редактора                        | `settings` + подстановка        |
| **пресет**        | сеть `omnifield-gateway` · peer-alias · ноль host-портов · общие тома · ассистент внутри                              | `presets.omnifield` + ветвление |

**Пресет, а не второй обвес.** Два источника не могут делить один файл
(`kb:BASER2-6`): «базовый + надстройка omnifield» выражается ИМЕНОВАННЫМ НАБОРОМ
ЗНАЧЕНИЙ внутри одного обвеса, а не вторым источником поверх первого. Отсюда же
требование к языку шаблона: без ветвления третий слой невыразим, поэтому форма
даёт `<% if %>`, а не только подстановку.

Слои не смешиваются проверяемо: `test/layers.spec.mjs` раскладывает обвес трижды
— без пресета, с пресетом и с заполненными значениями — и отдельно проверяет,
что универсальное переживает СНЯТИЕ пресета. Слой, который держится только
пресетом, универсальным не является.

## Настройки

| ключ               | тип       | дефолт                                            |
| ------------------ | --------- | ------------------------------------------------- |
| `name`             | `string`  | `<репозиторий>-devbox` (вычисляемый)              |
| `image`            | `string`  | `mcr.microsoft.com/devcontainers/typescript-node` |
| `runtimeVersion`   | `string`  | `24` (вычисляемый — пин выпуска, см. ниже)        |
| `installCommand`   | `string`  | `pnpm install --frozen-lockfile`                  |
| `editorExtensions` | `list`    | `esbenp.prettier-vscode`, `nrwl.angular-console`  |
| `network`          | `string`  | `null` — пресет ставит `omnifield-gateway`        |
| `networkAlias`     | `string`  | `<репозиторий>` (вычисляемый)                     |
| `secretsVolume`    | `string`  | `null` — пресет ставит `omnifield-secrets`        |
| `pnpmStoreVolume`  | `string`  | `null` — пресет ставит `omnifield-pnpm-store`     |
| `installAssistant` | `boolean` | `false` — пресет ставит `true`                    |

Не заполнил — идёшь за нашим выпуском. Заполнил — не поднимется никогда: движок
в конфиг пользователя не пишет, подниматься физически неоткуда (`kb:BASER2-5`).

## Версия рантайма: почему `24` и откуда это число

**Это решение выпуска, а не константа.** Резолвер обязан быть синхронной чистой
функцией без сети (`packages/baser-contracts/README.md` §3), поэтому «последняя
стабильная» не может вычисляться в момент установки — за ней пришлось бы идти в
реестр, а дефолт, ездящий по календарю, ломает воспроизводимость коммита.
Значит версия **пинится при выпуске обвеса** и двигается вместе с его версией:
видно в диффе, видно в ревью, одинаково на любой машине и в оффлайне.

Пин выпуска `0.1.0` — **Node 24**, и оснований два, оба проверяемых:

1. **Node 24 «Krypton» — Active LTS на дату выпуска** (2026-07-27). По графику
   релизов Node.js: 24 в Active LTS с 2025-10-28 по 2026-10-20. Линия 22 ушла в
   maintenance 2025-10-21 — выпускать сегодня обвес с дефолтом на
   maintenance-линии значило бы отдавать новому потребителю заведомо стареющий
   рантайм. Линия 26 вышла в апреле 2026, но Active LTS станет только
   2026-10-20: «последняя стабильная» — это LTS, а не Current.
2. **Тег реально опубликован семейством образа.** У
   `mcr.microsoft.com/devcontainers/typescript-node` на 2026-07-27 есть теги
   `18`/`20`/`22`/`24` и НЕТ `26` — семейство само идёт за LTS. Дефолт,
   указывающий на несуществующий тег, — сломанный девбокс, а не смелый.

**Когда двигать:** следующая чётная линия входит в Active LTS (ближайшая точка —
2026-10-20, Node 26) И семейство образа опубликовало соответствующий тег.
Движение дверь назовёт потребителю до применения («подниму версию с 24 на 26») —
спрашивать она не будет и не должна.

Обоснование живёт в `defaults.mjs` рядом с той строкой, которую придётся
переписать, а число зафиксировано тестом: молча двинуть его правкой одной строки
нельзя.

## Приёмка

**Зелёные тесты закрытием не являются.** Приёмка этой зоны — утверждение, а не
прогон: _обвес, поставленный КАК ПАКЕТ, раскладывается дверью в чистое дерево, и
результат совпадает с живым `.devcontainer` этого репозитория с точностью до
настроек._

```
npx vitest run --config packages/baser-devbox/vitest.config.mts
```

| файл                   | что доказывает                                                                  |
| ---------------------- | ------------------------------------------------------------------------------- |
| `acceptance.spec.mjs`  | приёмка целиком: тарбол → `node_modules` → дверь → диск → сверка с живым файлом |
| `declaration.spec.mjs` | обвес объявляет ровно то, что реально уехало в тарболе                          |
| `layers.spec.mjs`      | три слоя выражены и не смешиваются                                              |
| `defaults.spec.mjs`    | резолверы синхронны, чисты, без сети; пин конкретный, а не `latest`             |

Всё меряется по **распакованному `npm pack`**, а не по каталогу монорепы
(`test/packed.mjs`). Это ровно та проверка, которой у примера внутри чужого
пакета быть не могло: пока обвес жил каталогом, «объявил» и «лежит» были одним и
тем же фактом. Как только он стал пакетом, между ними встал `files` — и они
получили право разойтись молча:

| что не уехало    | как ломается у потребителя                    |
| ---------------- | --------------------------------------------- |
| `contentRoot`    | движок не находит источник: `missing-source`  |
| один `src`       | тот же отказ, но на одном артефакте из двух   |
| `defaultFrom`    | `resolver-failed` при первом же прогоне двери |
| `./package.json` | дверь вообще не находит пакет: `not-found`    |

Проверено мутацией на дереве, где всё зелено: убрать `defaults.mjs` из `files` —
22 теста из 43 падают, ещё 12 не доходят до прогона; соврать в `contentRoot` —
падают 27. Проверка, которую нельзя провалить, ничего не проверяет.

### Расхождения с живым файлом — названы поимённо

Приёмка не сверяет «примерно»: она считает список различающихся строк и
проверяет его ЦЕЛИКОМ. Расхождения ровно два, оба на настройках:

| строка                    | почему                                                                                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2 — комментарий-заголовок | в живом файле руками написано «baser devbox», обвес подставляет `name` → «baser-devbox». Прозаическое, не структурное; то же расхождение назвала проба формы   |
| 8 — `"image"`             | живой репозиторий стоит на Node 22, дефолт выпуска — 24. Это и есть «до настроек»: заполни `runtimeVersion: "22"` — расхождение исчезает, и это отдельный тест |

Структурных расхождений нет: остальные строки сверяются точно.

## Чего в пакете намеренно нет

- **Сборки и `dist`.** `defaultFrom` дверь резолвит путём внутри распакованного
  пакета, а не через `exports`: «собранный dist» означал бы, что обвес не
  работает до сборки — то есть не работает у потребителя.
- **Точки входа `.`.** Импортировать здесь нечего. `exports` называет ровно два
  адреса: `./package.json` (по нему дверь находит пакет) и `./defaults.mjs` (его
  зовёт она же).
- **Зависимостей.** Ни на дверь, ни на форму: обвес — контент. Прогон приёмки
  зовёт дверь из монорепы напрямую по пути, а у потребителя дверь стоит своим
  пакетом рядом.
- **Второго обвеса на тот же файл.** См. `kb:BASER2-6`.

## Известные шероховатости

- **Универсальный слой цитирует внутреннюю KB.** В шапке артефакта стоят
  `kb:ADR-16`, `kb:FUND-4`, `kb:ADR-20` — для внешнего пользователя это шум.
  Убрать их сейчас значило бы разойтись с живым `.devcontainer`, то есть с
  эталоном приёмки; правится вместе с ним, отдельным решением.
- **Копия обвеса в `packages/baser-contracts/examples/devbox`.** Проба формы и
  приёмка двери всё ещё гоняются по ней, а не по этому пакету. Две копии одного
  обвеса разъедутся — с этого выпуска они уже разъехались на версии Node
  (пример: 22, пакет: 24). Свести их — задача соседних зон.
