# `@omnifield/baser-contracts` — хвостовик

**Форма, которой обвес объявляет себя станку.** Станок не знает, что за инструмент
в патроне, — он знает форму крепления (`kb:BASER2-4`). Против этой формы программируют
три зоны: дверь (`baser-cli`) её читает и склеивает, обвес (`baser-devbox`) её
заполняет, движок (`baser-materialize`) говорит её словарём.

> **Статус: форма 2, принята architect** (`tasker:BASER2-10`, родитель — `tasker:BASER2-48`),
> реализация здесь же. Форма версионирована — см. `formVersion`.

Пакет **ничего не читает и ничего не исполняет**: ни файловой системы, ни сети, ни
загрузки чужих модулей. JSON и разобранный YAML подаёт дверь, резолверы зовёт тоже
она. Здесь — только форма и её пригодность.

## Что нового в форме 2

Форма 1 держала один инструмент за раз и всё, что настроил человек, — в `baser.json`.
Четыре изменения, и они дописывают одно объявление, поэтому поехали одним заходом
(`tasker:BASER2-10`):

|                           | было (форма 1)              | стало (форма 2)                                                            |
| ------------------------- | --------------------------- | -------------------------------------------------------------------------- |
| **класс артефакта**       | все файлы перегенерируются  | у записи раскладки есть `class`: `regenerated` (умолчание) · `placed-once` |
| **версия обвеса**         | —                           | берётся из манифеста пакета; вторым полем не заводится                     |
| **настройки потребителя** | `baser.json`, внутри записи | `.omnifield/<поставщик>-<обвес>.yaml`, ключ `baser`                        |
| **старое объявление**     | —                           | `formVersion: 1` получает названный отказ ЦЕЛИКОМ                          |

Переезд стоил ноль миграций: живых `baser.json` не существовало ни одного, и второго
такого дешёвого момента не будет.

## Три файла, и они не симметричны

|                            | Кто пишет       | Где лежит                                           | Что в нём                           |
| -------------------------- | --------------- | --------------------------------------------------- | ----------------------------------- |
| **объявление обвеса**      | поставщик       | `package.json` пакета обвеса, блок `baser`          | кто он, что кладёт, какие настройки |
| **перечень поставленного** | дверь и человек | `baser.json` в корне репозитория                    | какие обвесы поставлены             |
| **настройки обвеса**       | человек         | `.omnifield/<поставщик>-<обвес>.yaml`, ключ `baser` | пресеты и заполненные значения      |

Асимметрия принципиальная. **Раскладку объявляет обвес, а не потребитель**
(`kb:BASER2-5`): новый файл в шаблоне приезжает сам, пользователь ради этого свой
конфиг не правит. В файлах потребителя нет ни одного пути — только имена и значения.

**Файлами потребителя движок не владеет и ничего оттуда не чистит — только читает.**
Они рождаются сразу пользовательскими, поэтому режим владения им не нужен.

Настоящая декларация размазана по нескольким файлам в разных пакетах, и склеить их
может только дверь: у неё есть и то, и другое, и разрешение значений.

## 1. Объявление обвеса

```jsonc
// packages/baser-devbox/package.json
{
  "name": "@omnifield/baser-devbox",
  "version": "0.1.0", // ← версия обвеса живёт ЗДЕСЬ, и только здесь
  "baser": {
    "formVersion": 2,
    "source": {
      "id": "omnifield/devbox", // идентичность обвеса
      "title": "Девбокс: проект целиком в контейнере",
      "contentRoot": "template", // корень содержимого внутри пакета
    },
    "settings": {
      /* §3 */
    },
    "presets": {
      /* §4 */
    },
    "layout": [
      /* §5 */
    ],
  },
}
```

Блок называется по тому, **кто его читает**, а не по тому, чья экосистема, — как
`prettier`, `jest` и `packageManager`. Обвесы пишут посторонние (`kb:BASER2-7`), и
человек объявляет в своём `package.json` конфиг для инструмента, а не блок с именем
чужой организации. Чужому продукту понадобится своё объявление — он берёт свой ключ,
а не расширяет наш.

### `formVersion` — версия формы

Обязательна. Форма поедет, а выпущенные обвесы останутся в проде: без признака версии
старый обвес при изменившейся форме сломался бы **молча** или, хуже, был бы разобран
наполовину. Причина та же, по которой у движка есть `OUTPUT_SCHEMA_VERSION` —
несовместимость обязана быть видимой, а не выясняться по симптомам.

**Версия разбирается первой и в одиночку.** Не сойдясь на ней, разбирать нечего:
обвес чужой формы держит поля не там, где их ищет эта. Поэтому и обвес из будущего
(`formVersion` больше нашего), и обвес формы 1 получают отказ **целиком**, а не
частичный разбор, — и отказ называет, чем именно форма разошлась.

### `source.id` — идентичность

Строка вида `<поставщик>/<обвес>`, строчными. По ней группируется владение, ловится
столкновение, цепляется форк — и из неё же считается имя файла настроек у потребителя
(§6).

**`id` — не имя npm-пакета.** Пакет это доставка, `id` это личность: имя пакета
меняется (переезд scope, форк в свой пакет), а личность обвеса — нет.

Два обвеса с одинаковым `id` в одном репозитории — столкновение, называется вслух.

### Версии обвеса в объявлении нет

`source.version` не бывает: версия уже лежит в манифесте пакета рядом с `name`, дверь
её читает и показывает. **Второе место для одного факта — приглашение им разъехаться**,
и ровно на этом краснела приёмка `pack` (`tasker:BASER2-37`). Объявление с `version`
получает названный отказ, а не молчаливое «поля не знаю».

Версия при этом нужна: она попадает в запись паспорта укладки (`tasker:BASER2-52`) —
без неё нельзя ни сказать «между твоей версией и новой было ломающее изменение», ни
дать обвесу выполнить разовое действие при переходе.

## 2. Кто что делает со значениями

Порядок разрешения:

```
дефолт обвеса  →  пресеты (в порядке перечисления)  →  заполненное пользователем
```

Заполненное бьёт всё и не поднимается никогда: движок в конфиг пользователя не пишет,
подниматься физически неоткуда. Незаполненное едет за нами — обвес обновился, дефолт
поднялся, значение поднялось. **Движение дефолта дверь обязана назвать до применения**
(«подниму версию с 22 на 24»), а не спросить.

**Значения нужны двери, и только ей.** Дверь их разрешает, она же подставляет их в
содержимое, она же исполняет `render: false` и обязательство «не экранировать под
HTML». **Движок значений не получает вообще**: он берёт готовое содержимое через порт
`CanonSource` и кладёт артефакт целиком (`tasker:BASER2-23`).

Куда значение попадает внутри артефакта — дело шаблона. Пользователь видит настройку
с дефолтом, а не разметку файла.

## 3. Настройки: имя, дефолт, и всё

```jsonc
"settings": {
  "installCommand": {
    "title": "Команда установки зависимостей",
    "type": "string",
    "default": "pnpm install --frozen-lockfile"
  },
  "runtimeVersion": {
    "title": "Версия Node в образе",
    "description": "Последняя стабильная на момент выпуска обвеса.",
    "type": "string",
    "defaultFrom": "./defaults.js#latestStableNode"   // вычисляемый дефолт
  },
  "installAssistant": { "title": "Ставить ассистента внутрь", "type": "boolean", "default": false }
}
```

- `type` — `string` · `number` · `boolean` · `list` (список строк). Набор короткий
  намеренно: вложенные структуры превращают настройку обратно в разметку файла.
- `title` обязателен — настройку без имени человеку не показать. Он же вместе с
  `description` уезжает комментарием в файл настроек, который дверь рождает (§6).
- **Дефолт обязателен**: ровно одно из `default` / `defaultFrom`. Настройка без
  дефолта означала бы вопрос пользователю, а вопросов у двери нет (`tasker:BASER2-18`).
- `default: null` для `string`/`list` = «не задано»; шаблон такой блок не
  разворачивает. Для `number`/`boolean` «не задано» смысла не имеет: выключенный флаг
  это `false`, а не отсутствие флага.

### Вычисляемый дефолт — функция самого обвеса

`defaultFrom: "<файл внутри пакета>#<экспорт>"`. Станок функцию только зовёт и не
знает, что она считает, — как патрон не знает про фрезу. Закрытого списка «известных
вычислений» нет намеренно: он означал бы, что нетиповое приедет саморезами.

Расширение файла — то, которое пакет реально отдаёт (`.js` у собранного ESM-пакета,
`.mjs` у примеров в `examples/`): форма его не диктует, она берёт путь как есть.

```js
export function devboxName(ctx) {
  return `${ctx.repo.name}-devbox`;
}
```

Контекст даёт дверь: `{ repo: { name, root }, source: { id, packageName, version } }`.
`version` здесь — та самая версия из манифеста пакета; резолвер её получает, а
объявление её не дублирует.

**Резолвер — синхронная чистая функция локального контекста: репозиторий, пакет, файлы
рядом. В сеть не ходит.** Дефолт, ездящий по календарю («последняя стабильная на
сегодня»), ломает воспроизводимость коммита: один и тот же код поднимается по-разному
завтра и в оффлайне. Запинить вычисленное сегодня некуда — движок в конфиг
пользователя не пишет, а манифеста материализации ещё нет.

«Последняя стабильная» от этого не пропадает: она пинится **в самом обвесе** при его
выпуске. Тогда версия рантайма двигается вместе с версией обвеса — видно в диффе,
видно в ревью, воспроизводимо на любой машине. Пользовательская модель не меняется:
не заполнил — идёшь за нами; просто «за нами» означает «за нашим выпуском», а не «за
календарём». Дрейфующие дефолты вернутся после манифеста материализации, отдельным
решением.

Резолвер, вернувший обещание, — отказ (`resolver-async`).

### `defaultFrom` — это исполнение чужого кода

Дверь зовёт функцию из пакета обвеса. **Ставя обвес, ты исполняешь его код** — тот же
уровень доверия, что у любого npm-пакета с `postinstall`. Для наших обвесов это норма;
для комьюнити-обвесов (`kb:BASER2-7`) граница названа здесь, а не подразумевается.
Радиус ограничен тем, что резолвер — синхронная функция локального контекста без
сети. Политику доверия целиком форма не решает.

## 4. Пресет — ходовое положение регулировок

Пресет это **именованный набор значений настроек**, объявленный тем же обвесом. Не
второй обвес поверх первого: два источника не могут делить один файл (`kb:BASER2-6`),
поэтому уровни выражаются пресетом внутри одного обвеса.

```jsonc
"presets": {
  "omnifield": {
    "title": "Раскладка omnifield: общая сеть, общие тома, ассистент внутри",
    "values": { "network": "omnifield-gateway", "secretsVolume": "omnifield-secrets", "installAssistant": true }
  }
}
```

Простой обвес пресетов не объявляет и ничем за них не платит; продвинутый объявляет
сколько нужно — форма одна и та же (`kb:BASER2-4`). Пресет, выставляющий настройку,
которой обвес не объявлял, — отказ.

## 5. Раскладка — что, куда и на каких правах

```jsonc
"layout": [
  { "src": "devcontainer.json.ejs",  "dest": ".devcontainer/devcontainer.json" },
  { "src": "devcontainer-lock.json", "dest": ".devcontainer/devcontainer-lock.json", "render": false },
  { "src": "harness.yaml.ejs",       "dest": ".omnifield/harness.yaml", "class": "placed-once" }
]
```

- `src` — путь внутри `contentRoot`, `dest` — путь в репозитории потребителя. Имена
  им совпадать незачем: `src` — шаблон, `dest` — артефакт.
- `dest` — единица владения.
- `render` (по умолчанию `true`) — подставлять ли значения настроек. `false` для
  бинарного и для файлов, которые обязаны лечь байт в байт.
- `class` (по умолчанию `regenerated`) — чем станок держит артефакт, §5б.

Умолчания `render` и `class` проставляются при разборе, чтобы жить в одном месте, а не
в каждом читателе формы.

Режимов материализации в записи нет и не будет: `merge` отменён вместе со сведением
версий, `seed` выражается классом и форком источника. Оставшийся в объявлении `mode`
называется вслух как незнакомое поле, а не проглатывается.

## 5б. Класс артефакта — перечисление, а не флаг

**Станок даёт инструменту руки, а не решения** (`kb:BASER2-2` §4): он замечает и
называет, а что делать с файлом при обновлении — знает обвес. Он один знает, где у
него кор, где конфиг, а где скелет, в котором человек уже месяц работает. Класс — то
слово, которым обвес это говорит.

| класс         | что означает                                          |
| ------------- | ----------------------------------------------------- |
| `regenerated` | умолчание: артефакт наш и перегенерируется целиком    |
| `placed-once` | станок кладёт в объявленном месте и дальше не трогает |

Семантика `placed-once` (исполнение — `tasker:BASER2-51`):

- **хеш не пишем вовсе.** Записанный и никогда не сравниваемый хеш — половина имитации.
- **правка человека флага не поднимает,** и план его расходящимся не называет.
- **снятие не автоматическое.** Пропала запись из раскладки — `regenerated` уходит как
  сирота, `placed-once` НЕ уходит: называется вслух и снимается только явной командой.
  Иначе выпиленная строка шаблона молча уносила бы файл, в котором человек месяц работал.
- **пропал сам артефакт — кладём заново.** Это не «человек удалил, уважим», а
  «объявленное место пустое».

**Почему перечислением, а не `once: true`:** третий класс уже описан у соседей
(`kb:WEBER-4`), и флаг пришлось бы ломать при его приезде. `once: true` в объявлении
получает названный отказ с указанием на `class`.

## 5в. Язык подстановки

**Шаблоны обвесов пишутся на EJS** (пакет `ejs`) — том же, на котором работает
`generateFiles` у генераторов Nx, по форме которых устроен движок. Дверь
шаблонизатор не выбирает и второго не приносит: язык назван здесь, чтобы автор двери
и автор обвеса понимали под ним одно, а не разглядывали пример.

Пересказа документации EJS ниже нет — есть граница.

### Что обвесу доступно

|                   |                                                        |
| ----------------- | ------------------------------------------------------ |
| `<%- значение %>` | подстановка значения настройки, **как есть**           |
| `<% … %>`         | ветвление и перебор: `if`, `for`, локальные переменные |
| `<% … -%>`        | то же, со срезанием переноса строки за тегом           |

**Ветвление — несущая часть контракта, а не удобство.** Именно им выражается третий
слой обвеса: без пресета блок не разворачивается вовсе. Второго обвеса поверх первого
не бывает (`kb:BASER2-6`), уровни живут внутри одного — значит форма, дающая только
подстановку, не выражает девбокс.

### Чего нельзя

- **`<%= … %>` — запрещено.** Это экранирующая форма вывода: кавычка превращается в
  `&#34;`, и валидный `devcontainer.json` перестаёт быть JSON. Артефакты — это JSON и
  shell, а не разметка страницы. Всегда `<%-`.
- **`include(…)` — запрещено.** Шаблон тянул бы содержимое мимо объявленной раскладки:
  дверь не знает, откуда его резолвить, а `layout` перестал бы описывать то, что
  реально приезжает потребителю.

### На что опираться нельзя

В области видимости шаблона — **только разрешённые значения настроек, по именам**. Ни
контекста резолвера, ни переменных окружения, ни файловой системы, ни `require`. Всё,
что обвесу нужно вычислить, вычисляет его резолвер и приезжает настройкой.

### Кто это держит

Рендерит дверь, но **что разрешено, решает форма**: `checkTemplate(содержимое, адрес)`
называет чужой язык, экранирующую подстановку, `include` и оборванные теги. Дверь
зовёт её до рендера. Инвариант, который держит только соседняя зона, — не инвариант.

Отдельно про чужой язык: шаблон на Handlebars или Jinja EJS отрендерил бы **сам в
себя** — артефакт лёг бы к потребителю с неподставленным `{{ name }}` и ничем бы себя
не выдал. Поэтому запись с `render: true` без единого тега подстановки — отказ: либо
язык не тот, либо подставлять нечего и записи место под `render: false`.

`render: false` — файл копируется байт в байт и языком формы не меряется: это уже не
шаблон, а содержимое.

## 6. Сторона потребителя: что поставлено и как настроено

### `baser.json` — только перечень

```jsonc
// baser.json в корне репозитория пользователя
{
  "formVersion": 2,
  "sources": [
    { "use": "@omnifield/baser-devbox" },
    { "use": "@omnifield/brainer-agent-harness" },
  ],
}
```

- `formVersion` — **необязателен**: пишет его дверь при создании конфига, отсутствие
  означает самую старую разбираемую форму. Пользователь ничего не вводит — вопросов у
  двери не бывает, а миграционный крючок появляется. Причина та же, что у версии
  объявления: конфиги пользователей — такой же прод, как выпущенные обвесы, и
  молчаливая поломка там будет нашей виной, а не чужой. Номер общий с объявлением
  обвеса, потому что форма одна: дверь склеивает файлы в одну декларацию, и
  версионировать половинки порознь значило бы обещать совместимость, которой нет.
- `sources` — **список с первого дня**, а не единственный корень. Несколько
  поставщиков в одном репозитории — норма по построению (`kb:BASER2-2` §2).
- Путей здесь нет и не появится — см. асимметрию выше.
- `presets` и `settings` здесь больше не живут: запись с ними получает названный
  отказ, который говорит, КУДА они уехали. «Поля не знаю» отправило бы человека искать
  опечатку там, где её нет.

### `.omnifield/<поставщик>-<обвес>.yaml` — как настроено

```yaml
# .omnifield/omnifield-devbox.yaml
baser:
  presets: [omnifield]
  settings:
    runtimeVersion: '24'
    imageUser: vscode
# всё, что вне `baser`, — дело самого инструмента, дверь этого не читает
```

- **Имя считается из личности:** `source.id` (`omnifield/devbox`), слеш → дефис.
  Ссылки на конфиг в `baser.json` НЕТ намеренно: она была бы вторым местом для одного
  факта и могла бы разъехаться, а правило разъехаться не может.
- **Формат — YAML.** Файл заполняет человек, а человеку нужны комментарии: `title` и
  `description` каждой настройки обязаны попасть в файл, а не остаться в доке. Цена
  названа честно — у двери появляется зависимость на разборщик YAML. **Не у формы:**
  сюда приезжает уже разобранное значение (`parseSourceConfig`), пакет контрактов
  по-прежнему ничего не читает.
- **Зарезервирован один ключ — `baser`.** Всё остальное в файле принадлежит
  инструменту: у плагина агентов там живут зоны, модели и адреса сервисов, и дверь их
  не открывает. Один файл, два читателя, конфликта нет — пишет в него человек, а не
  два поставщика. Ключ назван так же, как блок в манифесте обвеса, по той же причине:
  блок называется по тому, кто его читает.
- **Опечатки называются вслух — но только внутри `baser`.** Незнакомый ключ в
  `baser.settings` значит «обвес такой настройки не объявлял», со списком объявленных.
  Вне `baser` дверь молчит, потому что это не её дело. Без зарезервированного ключа мы
  потеряли бы ловлю опечаток целиком.
- **Файла нет или он весь закомментирован — это не отказ,** а «ничего не выбрано»:
  работают дефолты обвеса.

### Кто этот файл рождает — уточнение к `kb:BASER2-5`

`kb:BASER2-5` говорит, что конфиг пользователя рождается сразу пользовательским и
движок его не кладёт. **Уточняем, а не отменяем: дверь создаёт файл настроек один раз,
если его нет, — с закомментированными дефолтами и описаниями. Значений она не пишет
никогда.** Инвариант «заполненное не поднимается, потому что движку писать некуда»
остаётся целым: после рождения дверь в файл не пишет ни при каких условиях. Рождение —
зона `cli` (`tasker:BASER2-53`); форма даёт имя (`sourceConfigPath`), ключ и разбор.

Файл настроек **не является записью раскладки и в паспорте укладки не числится**:
имена не сталкиваются по построению, владеть нечем.

### Исключение: путь диктует чужой инструмент

Конфиг, который посторонний инструмент ищет по фиксированному имени
(`.devcontainer/devcontainer.json`, `.claude/settings.json`), в общую папку **не
уезжает** — там его никто не прочитает. Обвес кладёт его обычной записью раскладки с
классом `placed-once`; дверь его не читает, инструмент получает своё там, где ждёт.
Граница из `kb:BASER2-2` («Конфиги человека — в одной папке»).

## 7. Один артефакт — один поставщик

Проверка над всеми поставленными обвесами сразу: **каждый `dest` встречается ровно
один раз**. Столкновение — названный отказ с обоими `id`, обоими пакетами и путём;
порядком записей оно **не** разрешается (`kb:BASER2-6`). Внутри одного обвеса две
записи на один `dest` — тот же отказ.

Совладения не бывает: движок кладёт артефакт целиком от одного владельца, а свести
вклад двоих можно было бы только сведением версий, которого нет.

Здесь же второе свойство набора: **у двух обвесов не бывает одного файла настроек.**
Имя считается из личности, слеш становится дефисом — и `a-b/c` сходится с `a/b-c`.
Случай экзотический, но не невозможный, а один файл на двоих означал бы, что каждый
называет чужие ключи опечатками. Молча такое не оставляем.

## 8. Что делает пакет

| Что                                                | Зачем                                                         |
| -------------------------------------------------- | ------------------------------------------------------------- |
| `readSourceDeclaration` · `parseSourceDeclaration` | разбор блока `baser` из манифеста обвеса                      |
| `parseConsumerConfig`                              | разбор `baser.json` — что поставлено                          |
| `parseSourceConfig` · `sourceConfigPath`           | разбор файла настроек и его имя из личности обвеса            |
| `resolveSettings`                                  | дефолт → пресеты → заполненное; порт `computeDefault` у двери |
| `checkTemplate`                                    | на том ли языке написан шаблон (§5в)                          |
| `checkSingleProvider`                              | карта владения (с классом) либо названные столкновения        |
| `ARTIFACT_CLASSES` · `DEFAULT_ARTIFACT_CLASS`      | классы артефакта и умолчание (§5б)                            |
| `FORM_VERSION` · `describeProblems`                | версия формы и текстовый рендер поверх тех же данных          |

Отказы — **данные, а не исключения**: разбор копит их и отдаёт списком с кодом,
адресом и человеческим текстом. Три опечатки это три опечатки, а не одна: бросок на
первой заставлял бы чинить их по одному прогону на штуку.

Единственное исключение — версия формы: она разбирается первой и её несовпадение
прекращает разбор, потому что дальше читать нечем.

Проверки здесь — про **пригодность объявления**, а не про безопасность чужого
действия. Движок отдельно проверяет пути, которыми пишет сам, и это не дубль:
инвариант, который держит только соседняя зона, — не инвариант.

## 9. Проба формы

```
npx vitest run --config packages/baser-contracts/vitest.config.mts
```

Приёмка формы была её выразительностью; приёмка реализации — обычная. Проба
(`src/lib/probe.spec.ts`) берёт **два живых обвеса этого репозитория** — `.devcontainer`
(девбокс) и `.omnifield/harness.yaml` (плагин агент-харнесса) — и прогоняет их через те
же валидаторы, что и настоящий обвес у двери:

| слой                               | что проверяет                                                                                        |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------- |
| несколько инструментов сразу       | одна карта владения на двоих, столкновений нет                                                       |
| класс артефакта                    | `regenerated` у девбокса, `placed-once` у конфига харнесса                                           |
| файл настроек                      | у каждого свой, имя из личности; чужая половина файла двери не мешает                                |
| универсальное + настройки + пресет | результат сходится с файлом на диске; ноль вопросов пользователю                                     |
| универсальное                      | тот же обвес без пресета — валидный devcontainer без сети и томов                                    |
| настройки                          | заполненное значение бьёт пресет (`24` вместо `22`, `npm ci`)                                        |
| язык подстановки                   | тот же шаблон, переписанный на Handlebars, — отказ; `<%=` — отказ                                    |
| отказы                             | форма 1 · настройки в `baser.json` · два обвеса на один `dest` · незнакомый ключ · обвес без дефолта |

Проба зовёт `checkTemplate` перед каждым рендером, поэтому язык подстановки проверяется
не отдельным тестом, а всем прогоном сразу. YAML и EJS она берёт теми же пакетами,
которыми будет пользоваться дверь, — своих зависимостей на них у формы нет.

Два расхождения с живыми файлами названы в самой пробе. У девбокса — прозаическое: во
второй строке руками написано «baser devbox», а обвес на её месте подставляет настройку
`name`; остальные строки сверяются точно. У харнесса расхождение **структурное и
законное**: `.omnifield/harness.yaml` объявлен `placed-once`, дальше файлом владеет
продукт, и правки в нём — не расхождение, а работа человека; поэтому сверяется то, что
кладёт обвес, а не файл целиком.

## 10. Чего здесь намеренно нет

Форк · манифест материализации · состояние источника. Форма под них не подстраивается,
но и не перекрывает им дорогу: `sources` — список, `id` отделён от имени пакета, класс
артефакта — перечисление, готовое принять третье слово.

Версионированы обе стороны формы: объявление обвеса — обязательно, конфиг потребителя
— необязательно, признак пишет дверь (§6).

Исполнения здесь тоже нет: класс в плане и версия в паспорте — движок
(`tasker:BASER2-51`, `tasker:BASER2-52`), чтение YAML и рождение файла настроек — дверь
(`tasker:BASER2-53`). Форма даёт слова, против которых они программируют.
