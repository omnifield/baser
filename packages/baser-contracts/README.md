# `@omnifield/baser-contracts` — хвостовик

**Форма, которой обвес объявляет себя станку.** Станок не знает, что за инструмент
в патроне, — он знает форму крепления (`kb:BASER2-4`). Против этой формы программируют
три зоны: движок (`baser-materialize`) её читает, дверь (`baser-cli`) по ней собирает
вход движку, обвес (`baser-devbox`) её заполняет.

> **Статус: НА СОГЛАСОВАНИИ.** Приёмка за architect (`tasker:BASER2-19`, шов
> `tasker:BASER2-1`). До приёмки против формы не программируем.

## Две стороны, и они не симметричны

| | Кто пишет | Где лежит | Что в нём |
|---|---|---|---|
| **объявление обвеса** | поставщик | `package.json` пакета обвеса, блок `baser` | кто он, что кладёт, какие у него настройки |
| **конфиг потребителя** | пользователь | `baser.json` в корне его репозитория | какие обвесы поставлены и чем они у него настроены |

Асимметрия принципиальная. **Раскладку объявляет обвес, а не потребитель**
(`kb:BASER2-5`): новый файл в шаблоне приезжает сам, пользователь ради этого свой
конфиг не правит. В конфиге потребителя нет ни одного пути — только имена и значения.

**Конфиг потребителя движок не кладёт, не владеет им и ничего оттуда не чистит —
только читает.** Он рождается сразу пользовательским, поэтому режим владения ему
не нужен.

## 1. Объявление обвеса

```jsonc
// packages/baser-devbox/package.json
{
  "name": "@omnifield/baser-devbox",
  "version": "0.1.0",
  "baser": {
    "source": {
      "id": "omnifield/devbox",              // идентичность обвеса
      "title": "Девбокс: проект целиком в контейнере",
      "contentRoot": "template"              // корень содержимого внутри пакета
    },
    "settings": { /* §2 */ },
    "presets":  { /* §3 */ },
    "layout":   [ /* §4 */ ]
  }
}
```

### `source.id` — идентичность

Строка вида `<поставщик>/<обвес>`. По ней группируется владение, ловится
столкновение и — дальше — цепляется форк.

**`id` — не имя npm-пакета.** Пакет это доставка, `id` это личность: имя пакета
меняется (переезд scope, форк в свой пакет), а личность обвеса — нет. Дверь
записывает и то и другое: `id` — как идентичность, `имя@версия` — как чем привезли.

Два обвеса с одинаковым `id` в одном репозитории — столкновение, называется вслух.

## 2. Настройки: имя, дефолт, и всё

```jsonc
"settings": {
  "installCommand": {
    "title": "Команда установки зависимостей",
    "type": "string",
    "default": "pnpm install --frozen-lockfile"
  },
  "runtimeVersion": {
    "title": "Версия Node в образе",
    "description": "Последняя стабильная на момент прогона.",
    "type": "string",
    "defaultFrom": "./defaults.js#latestStableNode"   // вычисляемый дефолт
  },
  "installAssistant": { "title": "Ставить ассистента внутрь", "type": "boolean", "default": false }
}
```

- `type` — `string` · `number` · `boolean` · `list` (список строк).
- **Дефолт обязателен**: ровно одно из `default` / `defaultFrom`. Настройка без
  дефолта означала бы вопрос пользователю, а вопросов у двери нет (`tasker:BASER2-18`).
- `default: null` для `string`/`list` = «не задано»; шаблон такой блок не разворачивает.
- **Куда значение попадает внутри артефакта — дело шаблона.** Ни пользователь, ни
  движок разметки файла не знают: пользователь видит настройку с дефолтом, движок —
  пару «имя → значение».

### Вычисляемый дефолт — функция самого обвеса

`defaultFrom: "<файл внутри пакета>#<экспорт>"`. Станок функцию только зовёт и не
знает, что она считает, — ровно как патрон не знает про фрезу. Закрытого списка
«известных вычислений» нет намеренно: он бы означал, что нетиповое приедет саморезами.

```js
export function devboxName(ctx) { return `${ctx.repo.name}-devbox`; }
```

Контекст даёт дверь: `{ repo: { name, root }, source: { id, packageName, version } }`.
Резолвер может быть асинхронным (последняя стабильная версия — это запрос наружу).

**Вернуть обязан конкретное значение, не `latest`** (`kb:BASER2-5`): иначе один и
тот же коммит поднимается по-разному на разных машинах.

## 3. Пресет — ходовое положение регулировок

Пресет это **именованный набор значений настроек**, объявленный тем же обвесом.
Не второй обвес поверх первого: два источника не могут делить один файл
(`kb:BASER2-6`), поэтому уровни выражаются пресетом внутри одного обвеса.

```jsonc
"presets": {
  "omnifield": {
    "title": "Раскладка omnifield: общая сеть, общие тома, ассистент внутри",
    "values": { "network": "omnifield-gateway", "secretsVolume": "omnifield-secrets", "installAssistant": true }
  }
}
```

Простой обвес пресетов не объявляет и ничем за них не платит; продвинутый объявляет
сколько нужно — форма одна и та же (`kb:BASER2-4`).

### Порядок разрешения значений

```
дефолт обвеса  →  пресеты (в порядке перечисления)  →  заполненное пользователем
```

Заполненное пользователем бьёт всё. Незаполненное едет за нами: обвес обновился,
дефолт поднялся — значение поднялось. **Движение дефолта дверь обязана назвать до
применения** («подниму версию с 22 на 24»), а не спросить.

## 4. Раскладка — что и куда

```jsonc
"layout": [
  { "src": "devcontainer.json",      "dest": ".devcontainer/devcontainer.json" },
  { "src": "devcontainer-lock.json", "dest": ".devcontainer/devcontainer-lock.json", "render": false }
]
```

- `src` — путь внутри `contentRoot`, `dest` — путь в репозитории потребителя.
  `dest` — единица владения: артефакт перегенерируется целиком из шаблона.
- `render` (по умолчанию `true`) — подставлять ли настройки. `false` для бинарного
  и для файлов, которые обязаны лечь байт в байт.
- **Рендер не экранирует ничего под HTML.** Кавычка обязана остаться кавычкой:
  артефакты — это JSON и shell, а не разметка страницы. (Найдено пробой: дефолтный
  вывод шаблонизатора превращал `"` в `&#34;` и ломал валидный `devcontainer.json`.)

Режимов материализации в записи нет и не будет: `merge` отменён вместе со сведением
версий, `seed` выражается форком источника.

## 5. Конфиг потребителя

```jsonc
// baser.json в корне репозитория пользователя
{
  "sources": [
    {
      "use": "@omnifield/baser-devbox",   // чем привезли
      "presets": ["omnifield"],
      "settings": { "runtimeVersion": "24" }
    }
  ]
}
```

- `sources` — **список с первого дня**, а не единственный корень. Несколько
  поставщиков в одном репозитории — норма по построению (`kb:BASER2-2` §2), и форма,
  в которой это надо будет «расширять», сломала бы обе зоны.
- Путей здесь нет и не появится — см. асимметрию выше.
- **Незнакомый ключ настройки не чистится и не игнорируется молча** — называется
  вслух: «обвес такой настройки не объявлял, значение никуда не поедет». Опечатка,
  которая тихо ничего не делает, — это ровно то молчание, из-за которого затирание
  становилось дефектом.

## 6. Один артефакт — один поставщик

Проверка над всеми установленными источниками сразу: **каждый `dest` встречается
ровно один раз**. Столкновение — названная ошибка с обоими `id` и путём; порядком
записей оно **не** разрешается (`kb:BASER2-6`). Внутри одного обвеса два `layout` на
один `dest` — та же ошибка.

Совладения не бывает: движок кладёт артефакт целиком от одного владельца, а свести
вклад двоих можно было бы только сведением версий, которого нет.

## 7. Чего здесь намеренно нет

Форк · манифест материализации · состояние источника · много-источниковость целиком
(A2/A4/A5). Форма под них не подстраивается, но и не перекрывает им дорогу: `sources`
— список, `id` отделён от имени пакета.

## 8. Проба формы

```
node packages/baser-contracts/examples/devbox/probe.mjs
```

Приёмка формы — её выразительность, а не покрытие тестами. Проба берёт **живой
`.devcontainer` этого репозитория** и описывает его объявлением обвеса во всех трёх
слоях:

| слой | что проверяет |
|---|---|
| универсальное + настройки + пресет | результат сходится с файлом на диске |
| универсальное | тот же обвес без пресета — валидный devcontainer без сети и томов |
| настройки | заполненное значение бьёт пресет (`24` вместо `22`, `npm ci` вместо `pnpm`) |

Единственное расхождение названо в самой пробе: во второй строке живого файла руками
написано «baser devbox», а обвес на её месте подставляет настройку `name`.
Расхождение прозаическое, не структурное.
