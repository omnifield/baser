# `@omnifield/baser-check` — обвес подходит посадочному месту

**Одно обещание: «подходит или нет, и если нет, то почему».** На вход — каталог
распакованного обвеса, на выход — данные: все проблемы списком, у каждой код,
адрес и человеческий текст. Пакет ничего не производит, ничего не пишет и
ничего не исполняет.

> Раз посадочное место наше, то и мультиметр «проверь, что обвес встаёт» — наш
> (`kb:BASER2-9`). Пользователь остаётся ответственным за свой кастом, но обязан
> иметь способ узнать заранее, а не у потребителя.

> **Словарь.** Деталь — это то, что станок ПРОИЗВОДИТ, то есть сам продукт;
> обвес подходит **посадочному месту**, из которых патрон лишь одно
> (`kb:BASER2-4`). Прежняя пара слов («деталь подходит патрону») была
> расхождением внутри канона, а не самодеятельностью зоны; канон поправлен
> 2026-07-29 (`kb:BASER2-9`), зона приведена следом за ним.

Первое звено цепи `check → pack → выдача` (`tasker:BASER2-29`, задача
`tasker:BASER2-30`).

## Вход — каталог, а не имя пакета

```ts
import { checkPackage } from '@omnifield/baser-check';

const report = checkPackage('packages/baser-devbox');
if (!report.ok) {
  // report.problems — все причины сразу, а не первая
}
```

Имя пакета требует резолва, то есть уже установленной поставки в чьём-то
дереве. Каталог не требует ничего — поэтому одно и то же годится для пакета
монорепы, для распакованного тарбола и для чужого обвеса, принесённого руками
(`kb:BASER2-7`). Резолв по имени — работа двери, у которой есть репозиторий
потребителя.

## Что зовётся, а не переписывается

Форму судят **контракты**, и они остаются единственным местом, где она описана:

| Что                     | Откуда            | Что приезжает бесплатно                                                                    |
| ----------------------- | ----------------- | ------------------------------------------------------------------------------------------ |
| `readSourceDeclaration` | `baser-contracts` | версия формы, незнакомые поля, дефолты настроек, пресеты, столкновение `dest` в объявлении |
| `checkTemplate`         | `baser-contracts` | язык подстановки: `<%=`, `include(…)`, оборванные теги, чужой шаблонизатор                 |

Второй разбор рядом с первым однажды с ним разойдётся, и тогда «годен» у
проверки и «годен» у двери станут разными словами. Поэтому здесь их **зовут**.

## Что добавляет эта зона

Всё, чего у формы нет и быть не может, потому что она ничего не читает с диска.

| Слой          | Что сверяет                                                                                 |
| ------------- | ------------------------------------------------------------------------------------------- |
| `manifest`    | каталог существует, в нём есть `package.json`, у пакета есть имя                            |
| `declaration` | блок `baser` разбирается формой                                                             |
| `content`     | `contentRoot`, каждый `src` и каждый модуль `defaultFrom` реально лежат                     |
| `shipping`    | каждый ФАЙЛ из объявленных попадает в белый список `files`, то есть **уедет к потребителю** |
| `templates`   | содержимое рендеримых шаблонов прочитано и отдано форме                                     |

Слой `shipping` — не придирка. `files` это белый список npm: шаблон, забытый в
нём, лежит у автора на месте и проходит все его прогоны, а пропадает **ровно у
потребителя**. Именно тот отказ, о котором узнают у чужого человека.

**Корень содержимого поставка НЕ судит — и это осознанно.** `contentRoot`
сверяется слоем `content` (каталог обязан лежать), но в `files` его не ищут:
`files: ["template/*.json"]` не увозит каталог `template` как таковой, а увозит
часть того, что в нём лежит. Обвинение корня было бы и ложным, и бесполезным —
уедет каждый конкретный артефакт или нет, видно только по нему самому. Поэтому
`shipping` судит файлы раскладки и модули резолверов, а не корень.

Модуль вычисляемого дефолта проверяется по той же причине: он обязан
резолвиться из **состава пакета**, а не из каталога разработчика — каталога
разработчика у потребителя не будет.

## Ответ — данные

```ts
interface CheckReport {
  ok: boolean; // производная от problems, а не второй признак
  root: string;
  packageName: string | null;
  packageVersion: string | null;
  declaration: SourceDeclaration | null; // разобранное — следующему звену цепи
  shipping: ShippingList; // состав поставки, включая «неизвестно, и вот почему»
  stages: CheckStage[]; // что сверено, сколько и что пропущено
  problems: CheckProblem[]; // все причины сразу
  trace: CheckSpan[]; // замеры слоёв
  checkSchemaVersion: number; // версия формы ЭТОГО ответа
  formVersion: number; // версия формы объявления, которую поддерживает ЭТОТ baser
}
```

Три беды в обвесе — три строки, а не три прогона: отказы копятся и отдаются
списком. Ветвиться потребителю — **по коду**, не по тексту; человеческий текст
поверх этих же данных рисует дверь (`tasker:BASER2-29`), а не проверка.

> **`formVersion` в цепочке значит два разных предмета — читайте адрес, а не
> имя.** Здесь это версия формы, которую поддерживает **проверяющий** (константа
> контрактов, против которой сверяли). У соседнего звена, в описи выдачи
> `baser-pack`, поле с тем же именем — версия, которую объявил **сам обвес**.
> Версия обвеса доступна и отсюда: `declaration.formVersion`. Имена совпали, а
> предметы нет, и в цепочке `check → pack` эти поля лежат рядом.

Коды соседних зон принимаются как есть: `form-version-unsupported` от контрактов
и `content-missing` отсюда — разные починки в разных местах, и склеивать их в
один «обвес непригоден» значило бы сказать «что-то не так».

### Свои коды

| Код                    | Что случилось                                      |
| ---------------------- | -------------------------------------------------- |
| `root-missing`         | каталога обвеса нет                                |
| `manifest-missing`     | в каталоге нет `package.json`                      |
| `manifest-unreadable`  | `package.json` не разбирается как JSON             |
| `package-name-missing` | у пакета нет имени — потребителю нечем его назвать |
| `content-root-missing` | `contentRoot` объявлен, каталога нет               |
| `content-missing`      | запись раскладки ссылается на несуществующий файл  |
| `content-unreadable`   | файл есть, но не читается                          |
| `resolver-missing`     | модуля `defaultFrom` в поставке нет                |
| `not-shipped`          | файл есть, но `files` его не увезёт                |

### «Пропущено» — это не «чисто»

`stages` называет объём сверенного и причину каждого пропуска. Зелёная проба,
которая ничего не сверила, хуже отсутствующей: «годен» читается одинаково и
когда сверили шесть путей, и когда не сверили ни одного. Поэтому:

- непригодное объявление **пропускает** слои ниже с причиной («неизвестно, что
  искать в поставке») — а не выдаёт их за чистые. Отказы самого разбора при этом
  отданы все разом: список формы не обрывается;
- `files` без белого списка или с отрицанием даёт `shipping: skipped` и
  `ShippingList` вида `not-declared` / `undecidable` с причиной.

**«Нечем» и «нечего» — разные состояния, и различает их ПРИЧИНА, а не статус**
(`tasker:BASER2-130`). Машинных имён по-прежнему три (`ok` · `failed` ·
`skipped`): по статусу ветвятся снаружи — `baser-pack` считает им сверенные
слои, — и расширять этот словарь ради оттенка значило бы менять форму ответа
всей цепи. Оттенок несёт `reason`:

| Что случилось                                    | Прогон  | Причина читается           |
| ------------------------------------------------ | ------- | -------------------------- |
| сверять нечем: манифест не прочитан, форма не та | красный | «неизвестно, что искать»   |
| сверять нечего: ни одной рендеримой записи       | зелёный | итогом: «0 из N», работы не осталось |

Второй случай — единственный, где пропуск стоит рядом с зелёным вердиктом, и
именно там «пропущено» читалось как несделанная работа. Состояния «мерить было
что, но не стали» у слоя `templates` **не существует**: он либо читает все
найденные шаблоны, либо не запускается вовсе. Формулировка закреплена пробой на
**чужом** обвесе без подстановок — том самом, на котором наблюдение и сделано.

## Состав поставки разбирается не целиком — и это названо

Полная семантика упаковки живёт в npm (`files` + `.npmignore` + встроенные
правила). Переписывать её сюда значило бы завести вторую правду, которая
разъедется с первой на первом же выпуске. Разбираются формы, в которых ошибиться
нельзя: имя (совпадение на любой глубине, как в `.gitignore`), путь от корня
пакета, каталог со всем поддеревом, подстановки `*` · `**` · `?`, плюс точка
входа `main`, которую npm увозит всегда.

Отрицания (`!x`), классы (`[a-z]`) и группы (`{a,b}`) — **`undecidable`**, а не
молчаливое «годен».

## Чего здесь нет намеренно

- **Глубоких проверок.** Мультиметр, а не тестовый сокет (`kb:BASER2-9`):
  проверяется форма и поставка, то есть встаёт ли обвес. «Разумен ли этот
  devcontainer» — вопрос другого уровня инструментов и другой зоны.
- **Вызова резолвера.** Позвать `defaultFrom` значит исполнить чужой код — акт
  доверия, который совершает дверь при установке. Проверка отвечает за то, что
  модуль найдётся и уедет, а не за то, что он вернёт.
- **Текстового рендера.** Ответ — данные; текст поверх них печатает дверь.
- **Нормализации и сборки.** Это `baser-pack`, следующее звено.
- **Претензий к лишнему.** Файл в `contentRoot`, не объявленный раскладкой, —
  не отказ: обвес от него в посадочное место встаёт.

## Почему это пакет, а не двадцать строк в контрактах

Правило приёмки было названо прямо: пакет оправдан своей логикой и своими
тестами, а не реэкспортом соседа. Считаем по слоям — из пяти к контрактам
сводится один (`declaration`) и половина ещё одного (`templates`, где контракты
судят, а читает файл эта зона). Три слоя целиком свои, и все три существуют
ровно потому, что **контракты не читают диск и не должны начать**: пакет формы,
получивший файловую систему, перестал бы быть формой.

Ровно та же граница видна и с другой стороны: `checkTemplate` контрактов
принимает СОДЕРЖИМОЕ, а не путь. Кто-то обязан это содержимое прочитать — и это
не форма.

## Проба

```
npx vitest run --config packages/baser-check/vitest.config.mts
```

Приёмка идёт на **живом `packages/baser-devbox`** — том обвесе, который мы
выпускаем сами: проверка, годная только на выдуманном пакете, не проверена.
Дальше он ломается **по одному пункту** и каждый тест требует, чтобы назван был
именно этот пункт, а список не обрывался на первом. Отдельным прогоном три
поломки разных слоёв дают три строки сразу.

Сама проба проверена мутациями: убрана проверка — тесты краснеют (`isFile`
всегда истинен, корень содержимого не сверяется, резолверы не сверяются, язык
шаблона не судится, `shipsPath` всегда истинен, отрицание в `files`
проглатывается, поддерево не покрывается образцом).

Вторая приёмка идёт на **чужом** обвесе — установленном
`@omnifield/brainer-harness` из `node_modules`, который не рендерит ни одной
записи. Свой обвес такой случай не даёт, а формулировка «мерить нечего» нужна
ровно на нём; берётся он установленным, то есть ровно таким, каким его видит
потребитель. Та же формулировка закреплена и точечной поломкой живого девбокса —
чтобы проба не зависела от чужого выпуска.

Отдельной пробой закреплён **словарь**: отменённая пара слов не звучит ни в
`description` пакета, ни в заголовке этой доки, ни в одном модуле, уезжающем в
`dist`. Судится ровно то, что видит получатель поставки: вычищенное руками
держится только до следующей правки руками. Проба тоже проверена мутацией —
возвращённое слово в любом из трёх мест краснеет.
